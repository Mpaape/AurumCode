# AUR-521: trilha de auditoria e SARIF para o code scanning da org

## Contrato

Qualquer `aurumcode review` (`--base` ou `--pr`) pode escrever dois arquivos
adicionais, cada um só quando a flag correspondente é dada (zero flags =
comportamento de hoje, byte a byte):

- `--auditoria <arquivo>`: um registro JSON (`internal/render.AuditRecord`)
  com o digest da política, o SHA do workflow, o repositório, o SHA
  revisado, o modelo, o veredito, a decisão do gate (`pass`/`fail`/
  `inconclusive` + motivo), os achados que efetivamente reprovaram o gate
  (`blocking_findings`), as exceções aplicadas (`exceptions_applied`,
  sempre uma lista — vazia até a AUR-520 passar a preenchê-la) e a
  cobertura (completa ou não, com os arquivos que ficaram de fora).
- `--sarif <arquivo>`: um documento SARIF 2.1.0 (`internal/render.
  BuildSARIFLog`/`WriteSARIF`) com `tool.driver.rules` (um por `rule_id`
  citado, com o título da seção de skill quando dinâmico), `results` com
  `ruleId`, `level`, `message`, `location` (URI relativo ao repositório +
  `startLine`) e `partialFingerprints` com a impressão digital canônica do
  achado. Uma revisão inconclusiva ainda produz um SARIF estruturalmente
  válido: `invocations[0].executionSuccessful=false` e um
  `toolExecutionNotifications` nomeando o motivo (AC-004).

Ver `docs/configuration.md`'s "Trilha de auditoria e SARIF" section para a
sintaxe completa.

## A identidade canônica de achado (compartilhada com a AUR-494)

`internal/render.FindingFingerprint` (`internal/render/finding_identity.go`)
é a ÚNICA definição de "mesmo achado" neste projeto. Ela existe antes da
AUR-494 chegar de propósito: o card pede explicitamente que a impressão
digital seja "a mesma identidade de findings da AUR-494", então esta entrega
a define uma vez, documentada como canônica, para que a AUR-494 a importe em
vez de redefinir a sua própria.

A identidade é `RuleID + caminho normalizado + linha + contexto de código
normalizado` (sha256, hex). Nunca inclui:

- o texto livre do modelo isoladamente (`message`) — o modelo reformula a
  mesma explicação de execução para execução, o que faria a impressão
  digital variar sem o achado ter mudado;
- qualquer valor por chamada (relógio, nonce, PID) — exatamente o que
  MUT-001 ataca: uma impressão digital que muda a cada rodada para o MESMO
  achado quebra toda deduplicação/rastreamento por impressão digital (SARIF
  incluso).

`normalizeFindingPath`/`normalizeFindingContext` tornam a identidade estável
sob reformatação inofensiva (barra/backslash, `./`, espaços) sem esconder
uma mudança real de conteúdo.

## Decisões de design

- **Reaproveitar, nunca reimplementar, a decisão do gate.** `evaluateGate`
  (AUR-519, `cmd/aurumcode/policygate.go`) não foi alterado: esta entrega
  não quis arriscar um desacordo de assinatura com a AUR-520, que edita o
  mesmo arquivo em paralelo para as exceções. Em vez disso,
  `matchedBlockingFindings` (`cmd/aurumcode/aur521.go`) relê os mesmos
  helpers já públicos (`gate.Declared()`, `gate.Threshold()`,
  `effectiveSeverityRank`) para render os achados que bateram o limiar como
  `render.AuditFinding` estruturado, e `auditGateOutcome` espelha o mesmo
  switch que `publishPolicyGateStatus` já usa para nomear a decisão.
- **Redação em uma única passada, no sink.** `WriteAuditRecord`/`WriteSARIF`
  serializam a estrutura completa e então passam o texto inteiro pelo
  filtro único (`internal/security/redaction`, AUR-009) antes de gravar —
  a mesma defesa estrutural (chave/valor, cabeçalho de auth, forma de
  credencial) e o mesmo registro de segredo exato (`AURUM_SECRET_CANARY`)
  que qualquer outro sink deste processo usa. Isso é redundante com a
  redação que o motor de revisão já aplica a `issue.Message`/`Evidence`
  antes de retornar (AUR-432) — de propósito: esta é a defesa em
  profundidade do PRÓPRIO sink, não uma segunda oportunidade para a mesma
  falha passar.
- **`exceptions_applied` sempre presente, vazio até a AUR-520.** O card pede
  o campo documentado mesmo sem a AUR-520 implementada; `BuildAuditRecord`
  nunca o deixa `nil`/omitido, e a forma SARIF `suppressions` já existe e é
  testada com um achado sintético marcado (`SARIFFinding.Suppressed`) — a
  AUR-520 só precisa popular o dado real, nunca desenhar a forma.
- **`omitted_files` hoje é a união de `IgnoredPaths` e `FilteredPaths`**
  (`reviewCoverageBreakdown`, `cmd/aurumcode/passes.go) — os arquivos
  config-ocultados e os binários/grandes demais, ambos já rastreados por
  caminho. Omissões por orçamento de tokens (`Budget`) só chegam como
  contagem (`code_files_omitted`), nunca por caminho, porque o construtor
  de prompt nunca nomeia esses arquivos de volta para `cmd/aurumcode` —
  uma lacuna pré-existente deste card, não uma introduzida por ele.
- **`model` é o valor de `--modelo`/`opts.modelo`**, não o nome resolvido
  pelo provedor (que pode escolher o padrão do endpoint quando a flag fica
  vazia). Documentado como melhor esforço: o card não exige uma segunda
  chamada ao provedor só para nomear o modelo de volta.
- **`action.yml` não foi tocado.** `action.yml` invoca o binário por
  argumentos posicionais fixos que `scripts/action-entrypoint.sh` consome
  — e esse script está fora dos `paths` do card (só em `read_paths`).
  Adicionar `--auditoria`/`--sarif` por esse caminho exigiria editar o
  entrypoint; a trilha de auditoria/SARIF é, por desenho do card ("a
  política de segurança... vem embutida no workflow reutilizável exigido
  pela org"), uma responsabilidade do workflow reutilizável, não da Action
  Docker direta. `.github/workflows/review.yml` já chama o binário com uma
  lista de argumentos explícita (não posicional) e foi estendido ali.

## Lacuna conhecida: upload para o code scanning

`.github/workflows/review.yml` escreve os dois arquivos (dentro do
container, montados para fora) mas os passos de upload
(`github/codeql-action/upload-sarif` para o SARIF,
`actions/upload-artifact` para o registro de auditoria) estão **comentados,
com TODO**, porque este builder trabalhou offline e nenhum outro workflow
deste repositório já fixa essas duas actions por SHA (só
`actions/checkout`, `actions/configure-pages`, `actions/upload-pages-
artifact` e `actions/deploy-pages` — ações diferentes — já têm um SHA
confiável em `pages.yml`/`review.yml`). Inventar um SHA teria sido pior que
não fixar nada: um reviewer com acesso à rede precisa resolver o SHA real de
`github/codeql-action/upload-sarif` e de `actions/upload-artifact` (a mesma
versão already revisada pela org, se houver) e descomentar os dois passos
antes deste card fechar de ponta a ponta no code scanning real.
