# AUR-466 — the deterministic pass distinguishes secret from placeholder, fixture, and constant SQL

## Command

```
aurumcode review --base <ref> [--fail-on <level>] [--modelo <nome>] [--seguranca]
```

Same command AUR-435/AUR-442/AUR-462 published. This card does not add a
flag or change the output shape; it narrows what two of `--seguranca`'s
deterministic rules match, in `internal/review/rules/security.yml`.

## The measured defect (2026-08-14)

Run against a real, 55-commit Node repository the tool had never seen, the
pass reported 15 findings of severity `error`. Every sampled one was
false, and traced to exactly two rules:

- `security/hardcoded-secret` matched:
  - `README.md`: a documentation code block, `export
    GEMINI_API_KEY=sua-chave` — the value is the literal word "sua-chave"
    (Portuguese "your key"), a placeholder.
  - `lib/setup-snippets.mjs`: a help-text string that teaches the same
    export line, inside a JS string literal.
  - `test/tui-smoke.mjs`: `process.env.OPENAI_API_KEY = 'ttm-smoke-key'`,
    a test fixture.
  - `test/e2e.mjs`: `'sk-body-ULTRA-SECRET'` — a value a redaction test
    asserts ON; the fake value is the test's own subject.
- `security/sql-injection` matched `lib/db.mjs`:
  `'SELECT * FROM daily_rollups' + (where.length ? ' WHERE ' +
  where.join(' AND ') : '')` — a query built entirely from string
  CONSTANTS. The real values are bound later through `?` placeholders via
  `params.push(...)`, never concatenated into the string. Correct code.

One shared cause: both rules matched the FORM of the line (a keyword
followed by `=`/`+`, a quote nearby) and never looked at the VALUE or the
surrounding CONTEXT. With `--fail-on error` this blocks every pull
request touching these files, forever, for no reason — worse than
finding nothing, because a team correctly disables the gate and the tool
is worth less than zero.

## The fix

Both rules keep their id (the AUR-461 mirror in
`internal/prompt/rulecatalog.go` compares ids in both directions against
this catalog, so no id was added or renamed; only the two `pattern:`
values changed in place).

### `security/hardcoded-secret`

The value-shape class was `[0-9\-]` — a hyphen counted as "the digit
half" of the required letter+digit mix, so any hyphenated multi-word
phrase (`sua-chave`, `ttm-smoke-key`, `ULTRA-SECRET`) satisfied it with no
real randomness. The fix is `[0-9\-]` → `[0-9]` (all 4 occurrences, both
alternation branches: quoted and unquoted forms): the value must now
contain a real digit.

This is the "low entropy / dictionary word" placeholder signal from the
card's own design notes, made concrete the only way a line-level regexp
can check it without a dictionary: base64/hex/vendor-token secrets are,
statistically, essentially never digit-free, while hand-typed placeholder
words overwhelmingly are. All four measured false positives contain no
digit at all and are now excluded. Every existing true-positive fixture
value in this repository (`AURUM-FAKE-KEY-9000-2222`,
`AURUM-FAKE-PASSWORD-9000-1111`, `AURUM-FAKE-TOKEN-0000-0001`,
`AURUM-FAKE-WEBHOOK-0000-0003`) contains a digit and keeps matching
unchanged (AC-003).

Deliberately NOT used: an `EXAMPLE|SAMPLE|DUMMY|FAKE|TEST|SMOKE`
marker-word denylist, one candidate the card's own design notes raise.
Every existing true-positive fixture in this repository is itself named
`AURUM-FAKE-...`; that denylist would silence the rule's own regression
fixtures. `sk-body-ULTRA-SECRET`, one of the five measured false
positives, also contains none of those words and even carries a
real-looking `sk-` vendor prefix — a marker-word list would have missed
it regardless. The digit rule catches it because it is not the marker
words that distinguish it, it is the absence of randomness.

Known limitation, accepted deliberately: a real secret that happens to be
digit-free (some base64 alphabets can produce one) is now missed. The
project's own fixtures, and every publicly documented vendor key format
sampled while designing this fix, contain digits; widening past "requires
a digit" back toward "requires a hyphen or a digit" reintroduces the
measured false positives.

### `security/sql-injection`

The pattern was `(?i)\b(select|insert|update|delete)\b.*["']\s*\+` — it
required a quote-then-`+` to exist SOMEWHERE after the SQL verb, but never
looked at what followed that `+`. The false positive's own second `+`
(`' WHERE ' + where.join(' AND ')`) also happens to be followed by a bare
identifier (`where`), so simply requiring "an identifier after `+`"
without also restricting the search is not sufficient — it would still
match at the second `+`.

Two changes fix this together:

1. `.*` (unbounded, can skip past any `+`) becomes `[^+]*`. Go's RE2 has
   no lookahead, so this is what pins the match to the FIRST `+` after the
   verb — the character class structurally cannot cross a `+`, so the
   engine can never reach the line's second `+` while trying to satisfy
   this pattern.
2. The suffix gains `\s*[A-Za-z_$][\w$.]*`: that first `+` must be
   immediately followed by a bare identifier or dotted access — the same
   "does the RHS start with a real identifier character, not `(` or a
   quote" shape AUR-462 already established for XSS. The measured false
   positive's first `+` is followed by `(`, excluded structurally; the
   true-positive shape (`"..." + name`) is followed directly by the
   identifier `name`, still matched.

`tests/fixtures/review/vuln/content/02/src/db.py:8` and
`tests/unit/AUR-435.go`'s `aur435SQLInjectionLine` (`"SELECT id, name FROM
users WHERE name = '" + name + "'"`) both still match byte-for-byte
(AC-003).

Known limitation, accepted deliberately: a query built as `"SELECT " +
"FROM " + userInput` (verb literal concatenated with another literal
FIRST, the tainted value arriving on a LATER `+`) is missed, because the
pattern only inspects the first `+` after the verb. No fixture in this
repository takes that shape; widening past the first `+` reintroduces the
measured false positive.

## What is not attempted

- No path allowlist as the mechanism (`test/`, `lib/` are not treated
  specially). A real secret committed in a test file is still a real
  secret, and both fixes work purely on value shape / structural position
  within the line, not on file path.
- No severity change. Both rules stay `severity: error`.
- No AST or semantic analysis. Both fixes are still single-line regular
  expressions the security pass applies to added diff lines; no
  cross-line state was added to `internal/review/securitypass.go`.
- Markdown-fence / multi-line-string detection ("is this line inside a
  \`\`\` block or a string literal") was considered and rejected: the
  security pass has no cross-line state today, and adding it to detect
  fencing is exactly the scope creep the digit-based value check avoids.
  The digit rule already suppresses the README and help-text cases
  without needing to know they are documentation at all.
