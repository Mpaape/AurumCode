# AUR-577: scanners are registered engines

## Measured before (base 85209c53, audit of 2026-10-03)

- Adding a scanner touched 12-14 files and 5 lists: the const/switch of
  `gate.sources` (`config.GateConfig.ValidateSources`), the fixed pointer
  `QualityGatesConfig.Sast`, the `quality_gates.sast` block of
  `ApplyCentralPolicy`, `gate.OriginSAST`, the dedicated
  `gate.SASTContributor{SectionOrigin, Issues, Reason}`, the `SAST*` fields of
  `gatePipelineInputs`, `runSASTPass`/`realSemgrepRunner` in
  `cmd/aurumcode/sast_pass.go`, the session's `runSAST`, `RankReason`'s
  `SASTReason`.
- `SastConfig.Engine` was decorative: `EngineName()` returned "semgrep" and the
  runner called `analysis.NewRunner().Semgrep` without reading it.
- The SARIF rebuilt each finding's origin by a `rule|path|line` join with
  `BlockingFindings` and dropped every blocking finding no review issue
  carried: the Dependency-Track breach (`ssor_dtrack`) was in the audit and
  missing from the SARIF.
- `fmt.Sprintf("%s (rule %s)", f.Message, f.RuleID)` was written in three
  places (gate/sources.go, cmd sast_pass.go, cmd passes.go).
- The Semgrep execution lived in `internal/analysis/semgrep.go`, beside the
  embedded regex catalog and go vet.

## What changed

- `internal/scanner` (new): `Scanner{Name(); Run(ctx, Request) (Report,
  error)}`, `Report{Findings, Complete, Version}`, `Finding.ToIssue(origin)`
  (the one conversion; `analysis.Finding` is now an alias of
  `scanner.Finding`), `Request{Root, Trust, Options, Command}`, the registry
  (`Register`, `Lookup`, `Names`, `NamesIn`, `Categories`, `KnownSource`) of
  `Engine{Scanner, Category, Origin, Validate}`, and the `Executor` that runs
  an engine with a timeout and turns an error, a missing binary or
  `Complete=false` into the inconclusive reason
  `<category or name>_{unavailable,execution_error,invalid_output,incomplete}`
  (`FailureReason`), never into zero findings.
- `internal/scanner/semgrep`: the Semgrep engine (code moved from
  `internal/analysis/semgrep.go` with its tests, plus the PATH runner from
  cmd). Category `sast`, origin `sast`, option `rule_packs`. The policy flags
  `--disable-nosem` and `--x-ignore-semgrepignore-files` are kept under
  `Trust: TrustPolicy`. `internal/scanner/engines` is the closed list of
  compiled engines (one blank import each); `internal/config` imports it, so
  every binary that parses a configuration holds the engines.
- `internal/config`: `quality_gates.scanners: [{engine, enabled, required,
  fail_on, options}]` (`scanners.go`); `quality_gates.sast` is read as the
  `semgrep` entry (`SastConfig.AsScanner`, always `required`), and its
  `engine` must be a registered engine of category `sast`. `Parse` refuses an
  unknown engine (`quality_gates.scanners[<engine>].engine: unknown engine
  ... (registered: semgrep)`), an engine declared twice (sast alias
  included), a bad `fail_on` and options the engine refuses.
  `mergeScanners` (`scanners_policy.go`) replaces the `quality_gates.sast`
  block of `ApplyCentralPolicy`: engine by engine, a required policy entry
  wins and the repository's entry (including `enabled: false`) becomes the
  warning `<key> do config do repositório foi ignorado: a política central
  decide sozinha` (the same text as before for `quality_gates.sast`); a policy
  entry that is not required yields to the repository with its own named
  warning. `FromPolicy(engine)` records which effective entries are the
  policy's. `gate.sources` and `gate.triage` validate against skills,
  analysis and the registry (engine names and categories); `sast` remains the
  category of every SAST engine, and the error text keeps listing `skills,
  analysis, sast`.
- `internal/gate`: `sast.go` became `scanner.go` with `Scan` (entry, engine,
  section, issues, reason) and `ApplyScannerGate`; `ScannerContributor{Scans}`
  replaces `SASTContributor` (pipeline name `scanners`); `RankReason` reads
  `ScannerReason`. `SASTIssues`, `FoldSources` and `OriginSAST` are gone.
- `cmd/aurumcode`: `scanner_pass.go` replaces `sast_pass.go`: `runScanners`
  runs every enabled entry through `reviewDeps.scanners` (a
  `scanner.Executor`; the injected runner of the session is now the
  executor), `joinScanners` states each inconclusive scan. The gate phase
  passes the scans to the one contributor, the triage maps each scan by the
  engine's `Answers`. Nothing in cmd or gate names an engine.
- `internal/render/gatefindings.go`: `GateSARIFFindings`.

## One gate finding for the audit and the SARIF (AC-005)

`Result.BlockingFindings` is the one record of what counted: the audit's
`blocking_findings` is written from it, and the SARIF now reads every origin
from it too. The SARIF still lists the review's issues (they carry the
message, the code context for the fingerprint, the assessment and the
suppression, which the gate finding does not); the match by rule, path and
line only attaches the gate finding's origin to that issue. What changed is
that a blocking finding no issue carries is no longer dropped: it becomes its
own SARIF result with its origin (`ssor_dtrack`, origin `dtrack`, message
`ssor_dtrack (origem dtrack)`).

## Observable output

The Semgrep engine keeps the origin `sast`: the gate line (`origem sast,
secao <policy|repo>`), the inconclusive line (`SAST (semgrep, origem sast,
secao repo) inconclusivo (sast_unavailable)`), the limitation (`SAST
(Semgrep) inconclusivo: ...`), the audit and the SARIF are byte-identical
for every existing configuration, so AUR-497's block and the gate and sast
tutorials did not have to change. A new engine's origin is its name.

## Divergence recorded

configuration load error, as AUR-575 already recorded; this card keeps that
code and `TestAUR577UnknownEngineStopsTheReview` asserts exactly 1 with the
engine named on stderr and no report printed.
