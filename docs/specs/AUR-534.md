# AUR-534: Toolchain Go suportado e atualizado por automacao

> Documento historico do board. Para uso atual, consulte o [guia do produto](../README.md).

## Bloqueio critico para quem for integrar: `second-reader-go-v1`

`.board/bin/second-reader` (o segundo motor de revisao, que executa as
citacoes `Unit`/`Contract`/`Integration`/`E2E` de QUALQUER card Go fora do
sandbox do `oci-run`, contra o repositorio inteiro) usa
`.board/locks/oci/second-reader-go-v1.lock.json`, que pina
`golang@sha256:2414035b086e3c42b99654c8b26e6f5b1b1598080d65fd03c7f499552ff4dc94`
(go1.21.13) com `GOTOOLCHAIN=local` forcado. Esse lock **nao foi trocado por
este card** (instrucao explicita: so trocar se um card em voo o usasse, e
nenhum `card` isolado o usa hoje -- mas o mecanismo `second-reader` em si o
usa para TODO card Go, nao so um). Confirmado por execucao direta: um
`go build` dentro dessa imagem contra um `go.mod` com `go 1.27` falha com
`go: go.mod requires go >= 1.27 (running go 1.21.13; GOTOOLCHAIN=local)`.

**Consequencia pratica: a partir do commit em que este card integrar em
`main`, toda chamada `second-reader --card AUR-NNN` cujo card cite um
`*_test.go` (engine `go`) vai falhar com esse erro de toolchain -- nao por
causa do codigo do card, mas porque o segundo leitor roda contra o
`go.mod` da arvore inteira, que agora exige 1.27.** Isso bloqueia a revisao
independente de qualquer card Go em `review`/`validating` no momento da
integracao. `go-git-offline-v1` (`golang@sha256:4746d264...`, tambem
go1.21.13, usado por um profile local a um card) tem o mesmo problema mas
impacto menor: nenhum card em `backlog/ready/doing/review/validating/
blocked-on-owner` o declara hoje.

Nao corrigido por este builder porque a instrucao do card reserva essa
troca ao coordenador ("leave go-git-offline-v1/second-reader-go-v1 as is
unless you find a card in flight using them (document)") e o lock de
`second-reader-go-v1` pina uma imagem `golang` pura (nao a
`aurum-bootstrap-go-bash` deste card) com um padrao de montagem diferente
(cache de modulos do host, nao assado na imagem) -- trocar exige escolher e
confirmar um digest novo, decisao que este pass preferiu documentar a
tomar sem tempo para o escrutinio que ela merece. **Recomendacao: tratar
como bloqueador de integracao, resolvido no mesmo commit ou imediatamente
em seguida, antes de qualquer card Go entrar em `review`.**

## O que mudou

`go.mod` passa de `go 1.21` para `go 1.27`. Go 1.21 saiu de suporte em 2024;
uma ferramenta de compliance nao pode rodar sobre uma toolchain sem correcoes
de seguranca. Go 1.27 e a versao estavel atual na familia Go 1.2x (1.26 perde
suporte antes da proxima janela de manutencao deste board).

Nenhuma dependencia muda. `go.sum` e byte-idêntico antes e depois do salto
(`sha256:b9142883d8f8e46998f705fbcd9964d6f386e17381ddf95a0c3173c832ce25e8`);
so a diretiva `go` em `go.mod` muda.

## Imagem do toolchain

Nova imagem, de Dockerfile versionado no repositorio em
`.board/oci/images/go-bash-1.27/Dockerfile`:

```
FROM golang:1.27.1-alpine3.24@sha256:8a5910f31396cd4d89662f56c68b3ae31d374308270a1c3bd96672ee5ed43414
RUN apk add --no-cache bash
WORKDIR /opt/aurum-a006
COPY go.mod go.sum ./
RUN GOTOOLCHAIN=local GOPROXY=https://proxy.golang.org GOSUMDB=sum.golang.org go mod download
COPY .board/oci/images/go-bash-1.27/Dockerfile /opt/aurum-a006/toolchain.Dockerfile
ENV GOTOOLCHAIN=local GOPROXY=off GOSUMDB=off GONOSUMDB=*
```

Mesmo padrao de `bootstrap-readonly-v1/Dockerfile`: base pinada por digest,
`go.mod`/`go.sum` reais do repositorio copiados no build (modulo cache
assado na imagem, ja que a sealed run roda offline). Duas diferencas
deliberadas:

- Sem `ENTRYPOINT ["/bin/bash"]`. `go-sealed`, `go-shared` e `go-live` chamam
  a imagem com um comando explicito (`go ...` / `sleep infinity` / `...`) sem
  `--entrypoint=`; herdar o entrypoint de bash do `bootstrap-readonly-v1`
  faria cada chamada virar `/bin/bash go ...` e morrer. `oci-run` zera o
  entrypoint por conta propria, entao nao precisa de nenhum dos dois.
- A propria Dockerfile e copiada para dentro da imagem
  (`/opt/aurum-a006/toolchain.Dockerfile`), junto com o `go.mod`/`go.sum`
  assados. E a base da prova de AC-004: a suite roda dentro da imagem sem
  Docker disponivel, entao o unico jeito de provar "esta imagem nasceu deste
  Dockerfile exato, com este `go.mod`/`go.sum` exatos" de dentro do sandbox e
  comparar byte a byte o que foi assado contra o que foi materializado.

Build (fora de qualquer card, para reconstruir a imagem apos uma mudanca):

```
docker build -f .board/oci/images/go-bash-1.27/Dockerfile \
  -t aurum-bootstrap-go-bash:1.27.1-<data> .
docker image inspect -f '{{.Id}}' aurum-bootstrap-go-bash:1.27.1-<data>
```

O `.Id` resultante (neste Docker 29, com o containerd image store, igual ao
unico `RepoDigests` da imagem recem-construida) e o digest que entra em cada
lock como `aurum-bootstrap-go-bash@sha256:<id>`. Confirmado para esta troca:

```
sha256:99bbed33cc0ac22f6fe947f589b82930dff841c35e6f8817f9c9fbae2adedb40
```

Smoke test (replica o probe do `oci-run`):

```
docker run --rm --pull=never --network=none --read-only \
  --user 65534:65534 --cap-drop=ALL \
  --tmpfs /tmp:rw,nosuid,nodev,size=128m --entrypoint= \
  aurum-bootstrap-go-bash@sha256:99bbed33cc0ac22f6fe947f589b82930dff841c35e6f8817f9c9fbae2adedb40 \
  bash -c 'command -v bash && go version'
```

## Cadeia de digest

`oci-run` nunca le `registry.v1.json`; o unico caminho que vale e
`.board/oci/profiles/<nome>.json` + `.board/locks/oci/<nome>.lock.json`. A
troca:

1. `image` em cada lock `*.lock.json` passa a
   `aurum-bootstrap-go-bash@sha256:99bbed33cc0ac22f6fe947f589b82930dff841c35e6f8817f9c9fbae2adedb40`.
2. `lock_digest` em cada profile `.json` (o campo que `oci-run` de fato
   valida contra `sha256sum` do arquivo de lock) e recalculado do lock novo.
3. `.board/oci/profiles/registry.v1.json` (registro secundario, nao lido por
   nenhum script encontrado neste pass -- so documental) tem `lock_digest` e
   `image_set_digest` recalculados por entrada, usando o campo `lock` de
   **cada entrada**, nao o nome da chave. Isso importa porque a entrada
   `bootstrap-readonly-v1` desse arquivo aponta `lock` para
   `registry-v1.lock.json`, nao para `bootstrap-readonly-v1.lock.json` -- uma
   inconsistencia que ja existia antes deste card e que este card nao
   corrige, so preserva corretamente (o lock_digest de uma entrada tem que
   bater com o arquivo que a propria entrada nomeia, nao com o arquivo cujo
   nome parece corresponder).
4. `image_set_digest` = `sha256(printf '%s' "aurum-bootstrap-go-bash@sha256:<digest>")`,
   sem newline final -- formula confirmada reproduzindo o valor atual
   (`c12ef435...`) contra a imagem antiga antes de escrever qualquer valor
   novo.

Locks trocados (10, todos os que pinavam
`aurum-bootstrap-go-bash@sha256:e8521445a6c1bc7c017258e9c71caf8eb78ee254862582c5d57d8a79d9413084`):
`bootstrap-readonly-v1`, `docs-tool-offline-v1`, `fake-provider-v1`,
`fake-scm-offline-v1`, `go-unit-offline-v1`, `oci-conformance-v1`,
`parser-worker-v1`, `polyglot-toolchain-v1`, `registry-v1`,
`sqlite-offline-v1`. (O briefing inicial deste card citava 12; a contagem
real na arvore e 10 -- recomputada, nao assumida.)

Locks **nao** trocados, por pinarem uma imagem `golang` diferente, nao a
`aurum-bootstrap-go-bash`: `go-git-offline-v1`
(`golang@sha256:4746d26432a9117a5f58e95cb9f954ddf0de128e9d5816886514199316e4a2fb`)
e `second-reader-go-v1`
(`golang@sha256:2414035b086e3c42b99654c8b26e6f5b1b1598080d65fd03c7f499552ff4dc94`).
Nenhum card em `backlog/ready/doing/review/validating/blocked-on-owner`
declara esses dois profiles hoje (so `done`/`cancelled`), entao a troca nao
bloqueia nenhum trabalho em andamento.

### `.board/bootstrap/locks/go.yml` e `.board/bootstrap/locks.yml`

`go_version` passa a `1.27`; `go_mod_sha256` e recalculado do `go.mod` novo
(`go_sum_sha256` fica igual, porque `go.sum` nao mudou). O `identity` em
`locks.yml` e recalculado pela formula exata de `.board/bootstrap/verify.sh`
(sha256 das linhas `AUR-xxx sha256:<digest>` de cada um dos 6 filhos, em
ordem lexicografica, com newline final) -- reproduzida primeiro contra o
valor atual antes de ser confiada, e depois confirmada rodando
`bash .board/bootstrap/verify.sh .board/bootstrap`, que retorna `ok` com o
identity novo.

## Gap conhecido: `go-git-offline-v1` / `second-reader-go-v1` ficam quebrados para o go.mod novo

Essas duas imagens (nao trocadas, de proposito -- ver acima) tem Go
1.21.13 assado dentro, e os profiles que as usam forcam
`GOTOOLCHAIN=local`. Confirmado por execucao direta: um `go build` contra um
`go.mod` com `go 1.27` dentro do container `go-git-offline-v1`
(`golang@sha256:4746d264...`) falha com
`go: go.mod requires go >= 1.27 (running go 1.21.13; GOTOOLCHAIN=local)`.
Isso nao e um defeito deste card -- nenhum card em voo usa esses dois
profiles hoje -- mas e uma consequencia real do salto que o proximo card a
reusar `go-git-offline-v1` ou `second-reader-go-v1` vai bater de frente. Nao
corrigido aqui porque esta fora do escopo (`paths`) deste card e porque o
plano consultado explicitamente deixa essas duas imagens de lado.

## Automacao (AC-003)

`.github/dependabot.yml` cobre tres ecossistemas, todos semanais: `gomod`
(raiz), `docker` (raiz **e** `.board/oci/images/go-bash-1.27`, a nova
imagem) e `github-actions`. Limite conhecido: o Dependabot nao interpreta
imagem Docker dentro de uma linha `run:` de workflow -- ele so atualiza um
`FROM` em Dockerfile e a referencia de uma `uses:` action. As duas linhas
`docker run ... golang:1.27.1-...` em `.github/workflows/ci.yml` continuam
precisando de edicao manual quando a proxima versao sair. Isso nao bloqueia
AC-003 (que pede cobertura dos tres ecossistemas, nao automacao total de
toda referencia de imagem), mas e um limite real, nao "CI totalmente
automatizado".

Segundo limite, mais importante: mesmo o `FROM` que o Dependabot consegue
editar (`.board/oci/images/go-bash-1.27/Dockerfile`) nao fecha o ciclo por
si so. Um PR do Dependabot muda o digest base; ele nao builda a imagem, nao
calcula o novo `aurum-bootstrap-go-bash@sha256:...`, e nao atualiza os 10
locks, os 10 `lock_digest` de profile, nem o `registry.v1.json`. Esse e
exatamente o trabalho manual que a secao "Cadeia de digest" acima descreve
-- `docker build` + `docker image inspect -f '{{.Id}}'` + reescrever cada
lock/profile/registry com o digest novo. "Atualizado por automacao" (o
titulo deste card) vale para a DETECCAO de uma versao nova disponivel, nao
para o fechamento de toda a cadeia de digest sem intervencao humana.

  go-unit-offline-v1 --card AUR-534`, que materializa so `paths`+`read_paths`

  em `go-sealed` acima mostra -- a suite inteira passa, limpa, sob Go 1.27.
