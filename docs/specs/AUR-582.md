# AUR-582 — regra embutida de segredo lê a base pública do gitleaks como dado pinado

## Medido antes

- `internal/analysis/analysis.go` fixava em Go, por `regexp.MustCompile`, uma
  única regex de palavra-chave para `analysis/hardcoded-secret`
  (`password|token|secret... = "<8+ chars>"`): sem formatos de fornecedor, sem
  entropia, sem allowlist. Uma chave AWS ou um token GitHub atribuídos a um
  identificador neutro (`awsID := "AKIA..."`) não produziam achado.
- O lock `.board/bootstrap/locks/scanners.yml` já pina a base:
  `secrets_rulebase_id: gitleaks-default-config-v8.30.1` e
  `secrets_rulebase_sha256: sha256:e163e53b…caf` (97731 bytes,
  `https://raw.githubusercontent.com/gitleaks/gitleaks/v8.30.1/config/gitleaks.toml`).
  O download conferiu exatamente esse digest.

## O que mudou (v2)

- `internal/analysis/rules/secrets.json`: derivação JSON da configuração
  padrão do gitleaks v8.30.1 (id, descrição, regex, path, secretGroup,
  entropy, keywords, allowlists por regra e allowlist global), com
  `source.sha256` = `secrets_rulebase_sha256` do lock. O TOML de origem NÃO é
  commitado: o repositório é público e as allowlists da base trazem chaves de
  exemplo com forma de credencial.
- Literais de allowlist com forma de credencial — sem metacaractere de regex
  e casados pela regex da própria regra (hoje: os 16 exemplos `AIza…` de
  `gcp-api-key`) — vão para o JSON só como sha256 (`literal_sha256`). Os
  demais regexes de allowlist e as stopwords ficam em claro. Diferença de
  semântica registrada: na fonte, o regex de allowlist casava qualquer alvo
  que CONTIVESSE o literal (substring); aqui o alvo (`regexTarget`, por
  padrão o segredo capturado) é suprimido só por IGUALDADE exata de hash.
- `internal/analysis/rules/secrets.json.sha256`: digest dos bytes do JSON,
  checado pelo loader (pânico no init se divergir).
- `scripts/analysis/update-secret-rules.sh` (host com rede): lê versão e
  digest do lock, baixa o TOML na tag, recusa digest divergente, deriva o
  JSON com `python3`/`tomllib` (stdlib — nenhum parser TOML no `go.mod`),
  converte os literais com forma de credencial em hash (só se a regex da
  regra os casa), confere que cada regra derivada mantém id e regex da
  fonte, grava JSON e sidecar. `AURUMCODE_GITLEAKS_TOML_OUT=<arquivo>`
  guarda uma cópia do TOML verificado fora do repositório. Reexecutar o
  script deixa `internal/analysis/rules/` sem diff.
- `internal/analysis/rules/secrets-local.json`: a regra de palavra-chave
  anterior, agora como dado (`aurumcode-keyword-assignment`, contexto
  `code-outside-string-literals`). Justificativa: a base pública não cobre os
  casos existentes `password = "xxxxxxxx"`, `token = "zzzzzzzz"` etc. — o
  valor bate na allowlist global (`^(?i:a+|…|x+|…|z+)$`) e na entropia mínima.
  Manter a regra local preserva o comportamento publicado (mensagem fixa
  `Hardcoded secret or credential assigned inline`, usada por testes de
  `cmd/`, `tests/unit/AUR-505.go`, o tutorial `gate` e docs), e a supressão
  de exemplos dentro de string literal continua só nela.
- `internal/analysis/secretcatalog.go`: `go:embed` do JSON, do sidecar e da
  regra local; loader recusa schema desconhecido, digest de artefato
  divergente e `source.sha256` malformado. Regras sem regex (só `path`) e
  regex que o RE2 recuse viram `skipped`, nunca somem.
- `internal/analysis/secretscan.go`: semântica do gitleaks — pré-filtro por
  keywords, regex, segredo = `secretGroup` ou primeiro grupo não vazio ou o
  match, entropia de Shannon > mínimo, allowlists por regra e global
  (regexes e hashes com `regexTarget` secret/match/line, paths, stopwords,
  condição OR/AND). Regras locais primeiro, depois a base; no máximo um
  achado `analysis/hardcoded-secret` por linha; só linhas adicionadas, após
  remover comentários.
- Mensagem: regra local mantém a mensagem fixa; regra da base usa
  `Hardcoded secret matched rule <id> (<descrição>)`; o valor capturado nunca
  entra na mensagem. O id `analysis/hardcoded-secret` e as demais regras
  (injeção de comando/SQL, permissões) não mudam.

### Cadeia de digests (sem campo novo no lock)

lock (`secrets_rulebase_sha256`) → TOML (o script recusa outro digest) →
JSON (`source.sha256`, comparado ao lock pelo teste com
`AURUMCODE_SCANNERS_LOCK`) → bytes do JSON (`secrets.json.sha256`, checado no
loader). Um campo `secrets_rulebase_artifact_sha256` mudaria a identidade em
`locks.yml`, o bloco citado em `docs/tutorials/operacao.md` e entradas de
tutoriais e testes fora dos `paths`, sem ganho de prova: o sidecar já amarra
cada byte do artefato.

### Fidelidade à fonte (teste condicionado)

Como o TOML não está no repositório, `TestDerivedSecretCatalogFaithfulToSource`
só roda com `AURUMCODE_GITLEAKS_TOML=<cópia verificada>`; sem ela, pula com o
motivo explícito. Com ela, confere sha256 da fonte, número e ordem das
regras, id, regex e entropia, e que cada `literal_sha256` é o hash de um
literal da allowlist da regra de origem que a regex da própria regra casa.
O script faz a mesma conferência de id/regex em cada atualização. Rodado
localmente com a cópia baixada: `--- PASS: TestDerivedSecretCatalogFaithfulToSource`.

### Cobertura da base

222 regras; 221 compilam no `regexp` do Go. A única pulada é `pkcs12-file`
(regra só de path), fixada em `TestSkippedSecretRulesAreDeclared`. A
heurística do gitleaks de exigir dígito em segredos de regras `generic*` não
faz parte da configuração e não foi reproduzida.
