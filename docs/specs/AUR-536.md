# AUR-536 — Contexto local do PR só com árvore limpa e prova dos casos inverificáveis

Status: especificação do card AUR-536 (`O05-review`), follow-up da revisão de AUR-515.

## Problema

AUR-515 verifica que o checkout local é, de fato, o repositório revisado no
HEAD exato que o PR nomeia, antes de deixar `resolveCodebaseContext` ler esse
checkout. Mas repositório+HEAD corretos não implicam árvore limpa: uma edição
não commitada, um arquivo não rastreado, ou arquivos de um clone aninhado
continuam sentados no disco e `internal/context/resolver.go` os envia ao
modelo do mesmo jeito, já que seu `filepath.WalkDir` não tem nenhuma noção de
git. Além disso, o branch "inverificável" de `codebaseContextMismatch`
(diretório sem `.git`, checkout sem `origin`, falha da API ao buscar o head
do PR) nunca foi exercitado pelo `--pr` real — só a ausência/divergência de
repositório e HEAD tinham prova.

## Decisão

A verificação de árvore limpa fica em `cmd/aurumcode`, não em
`internal/context`: ela só se aplica ao caminho `--pr` (`pr.go`, logo depois
de `codebaseContextMismatch`), nunca ao `--base`, onde o checkout IS a mudança
sob revisão por construção (ver o comentário de pacote de `aur515.go`).
Colocar a verificação dentro do resolver genérico acoplaria um pacote sem
noção de git a semântica de git, e mudaria `--base` também — o resolver
continua lendo literalmente a árvore de trabalho, como hoje.

`internal/analyzer` tem o único leitor de objetos git do projeto
(`flattenTree`/`readTree`/`readCommit`), mas é todo não exportado, e este
card não escreve em `internal/analyzer` (`paths` não o inclui). A abordagem
preferida do card — restringir o conjunto percorrido aos caminhos
rastreados no HEAD cujo conteúdo bate com o blob commitado — portanto só é
viável reimplementando parte dessa leitura, não estendendo-a. `aur536.go`
faz isso com dois backends, escolhidos uma vez por chamada, no mesmo
espírito dual do `analyzer.OpenRepo`:

- **git no PATH** (imagem oficial, `Dockerfile` instala `git`): `git ls-tree
  -r -z HEAD` resolve o mapa caminho→blob exato, inclusive em repositórios
  com objetos empacotados. Cada arquivo da árvore de trabalho tem seu próprio
  id de blob git calculado aqui mesmo (`sha1("blob "+len+"\0"+conteúdo)`,
  sem subprocesso por arquivo) e comparado contra esse mapa; qualquer
  caminho ausente do mapa, com hash diferente, ou um caminho rastreado
  ausente no disco, é "dirty".
- **sem git no PATH** (perfil de aceite selado, sem rede e sem o binário):
  não há como listar a árvore do HEAD sem a API não exportada acima, então
  o fallback verifica, por arquivo, se o id de blob calculado já existe
  como objeto *loose* em `.git/objects` (reaproveitando `gitConfigPath`, de
  `aur515.go`, para achar o diretório de objetos certo mesmo atrás de um
  worktree vinculado). Existência de um objeto loose com esse nome é prova
  de que aquele conteúdo exato já foi commitado em algum momento deste
  repositório — mas não necessariamente no caminho revisado, e nunca em
  objetos empacotados. Isso é documentadamente mais fraco que o caminho com
  git: fecha em "inverificável" (fail-closed) para um clone real já
  empacotado. Não importa em produção, que sempre tem `git`; importa só
  para os fixtures pequenos, de objetos loose, que este card usa para
  provar o próprio comportamento sem o binário.

`codebaseContextReasonUnverifiable` (antes um literal repetido três vezes em
`aur515.go`) virou uma constante única, e `codebaseContextReasonDirty`
("dirty") ganhou um texto de limitação próprio em
`codebaseContextOmittedNotice`, distinto do texto genérico de
"inverificável" — necessário para que uma mutação que colapsa um motivo no
outro seja pega pelo teste certo, não mascarada por outro caminho que já
falha fechado por razões diferentes.

A documentação (`docs/getting-started.md`, `docs/configuration.md`) passa a
avisar quem monta a Action Docker diretamente (sem o workflow reutilizável):
sem um `actions/checkout` explícito em
`ref: ${{ github.event.pull_request.head.sha }}`, o padrão do
`actions/checkout` num evento `pull_request` é o merge ref sintético — um
commit que não é o head revisado —, e o contexto de codebase sai como
"inverificável" (reason `"head"`, de AUR-515). O workflow reutilizável
(`.github/workflows/review.yml`) já faz esse checkout correto e não muda.

## Prova

`cmd/aurumcode/aur536_test.go`, no mesmo molde httptest+
`AURUMCODE_LLM_FIXTURE` de `aur515_test.go`:

- `TestAUR536UntrackedFileOmitsContextFromPrompt` (AC-001): checkout
  verificado (repositório+HEAD corretos, árvore committed limpa) mais um
  arquivo não rastreado cujo caminho é o marcador do teste — o resolver só
  conseguiria expor esse caminho via uma referência ao símbolo commitado
  `aur515LocalMarker`, nunca via `Pack.Symbols` (que só vem dos caminhos do
  diff). O caminho não aparece no prompt capturado, e o parecer publicado
  declara a omissão com o texto específico de "dirty".
- `TestAUR536NoGitMetadataOmitsContext`,
  `TestAUR536NoOriginRemoteOmitsContext`,
  `TestAUR536PullRequestMetadataFailureOmitsContext` (AC-002): as três
  pernas de `codebaseContextMismatch` que já existiam, mas nunca tinham sido
  dirigidas pelo `--pr` real. As três omitem o contexto com o texto
  específico de "inverificável", e o marcador comitado nunca aparece no
  prompt.

`tests/acceptance/AUR-536.sh` roda os dois pacotes num clone isolado
(`go.mod go.sum cmd internal pkg`), com seletores `all`, `AC-001`, `AC-002` e
`AC-002-MUT-001`. A mutação colapsa a constante
`codebaseContextReasonUnverifiable` para `""` numa única linha (a
declaração), o que transforma as três pernas "inverificável" de
`codebaseContextMismatch` — e o próprio fallback de
`verifiedCleanCheckoutReason` — em "verificado" de uma vez só; as três
provas de AC-002 precisam virar RED. Verificado manualmente com o binário
`git` presente e com `PATH` sem `git` (simulando o perfil selado); os dois
backends concordam em todos os casos, inclusive nos testes herdados de
AUR-515.
