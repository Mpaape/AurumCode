# AUR-596: provedores de LLM conhecidos por configuração

## Medido antes (base dff46828)

- O Aurum falava um único dialeto: Chat Completions compatível com OpenAI em
  `internal/llm/provider/litellm`, com `Authorization: Bearer`, `max_tokens` e
  `response_format` (`json_schema` ou `json_object`), escolhido só por
  `LLM_API_KEY` + `LLM_BASE_URL`. A URL era sempre `<base>/chat/completions`.
- Um erro do provedor virava `LiteLLM API error (status N): <corpo cru>`, sem o
  nome do provedor, sem resumo e sem redação da chave ecoada no corpo.
- Uma resposta JSON sem lista de achados (`{"answer":"ok"}`) era decodificada
  como lista vazia: uma aprovação que o modelo nunca deu.
- Diretórios vazios `internal/llm/provider/{anthropic,openai,ollama}` sem uso.

## O que mudou

- `internal/llm/provider/profiles/profiles.yml` (embutido por `go:embed`): o
  catálogo declarativo de perfis — `openai-compatible` (padrão), `openai`,
  `azure-openai`, `anthropic`, `google`, `bedrock`, `litellm`, `openrouter`,
  `opencode`, `ollama`. Campos: `base_url` (com `{VAR}` e `{VAR:-padrão}`),
  `key_env`, `auth` (`bearer`|`header`|`none`), `auth_header`, `path`,
  `query`, `token_field` (`max_tokens`|`max_completion_tokens`),
  `structured_output` (`json_schema`|`json_object`|`none`).
- `profiles/catalog.go`: carrega e valida o catálogo (valor fora da lista falha
  ao carregar, nunca no fio); `Merge` aplica o arquivo do operador
  (`LLM_PROVIDERS_FILE`), que acrescenta ou substitui um perfil inteiro.
- `profiles/resolve.go`: `FromEnv` lê `LLM_PROVIDER`; ausente, devolve "não
  selecionado" e o caminho antigo segue intacto. Perfil desconhecido, chave
  ausente, `{VAR}` sem valor ou URL ausente são erro (nunca recaída
  silenciosa). Provedor, URL e chave vêm só do ambiente do operador, nunca da
  configuração do repositório revisado (por isso não há `llm.provider` no
  config do repositório).
- `litellm/dialect.go`: o `Dialect` aplicado pelo motor único (URL + path +
  query, autenticação, campo do limite, `response_format`). `DefaultDialect`
  reproduz o dialeto antigo; `NewProvider` o usa, então sem `LLM_PROVIDER` a
  requisição é byte a byte a de antes.
- `litellm/errors.go`: erro não-200 resumido à mensagem do envelope do
  provedor (OpenAI/Azure/OpenRouter/LiteLLM `{"error":{...}}`, Anthropic
  `{"type":"error","error":{...}}`, Google `{"error":{"status"...}}` ou lista,
  Bedrock `{"message":...}`), redigido (a chave e formas conhecidas de
  segredo) antes de truncar em 300 caracteres, com o nome do perfil.
- `internal/prompt`: resposta sem `issues`/`line_comments` é erro de validação
  `missing_issues` (revisão inconclusiva), para todo provedor.
- `cmd/aurumcode/main.go`: `providerFromEnv` consulta o catálogo antes do
  caminho antigo. `review_cache.go`: a URL resolvida pelo perfil entra na chave
  do cache quando `LLM_BASE_URL` está vazia (dois deployments Azure não
  compartilham entrada).
- `.github/workflows/providers-smoke.yml`: só `workflow_dispatch`; o job
  `detectar` lista provedores com secrets; matriz `smoke` só para esses;
  os demais aparecem como "não verificado"; sem nenhum secret a execução
  falha. `actions/checkout` pinado por SHA. `actionlint` limpo.
- Docs: `docs/provedores.md` (nova, no nav), links em `configuration.md` e
  `getting-started.md`, seção do servidor MCP do Aurum no OpenCode
  (`opencode.json`, chave `mcp`, `type: local`, `command: ["aurumcode","mcp"]`).
  Tutorial `demo/tutoriais/provedores` + `docs/tutorials/provedores.md`.
- Removidos os diretórios vazios `internal/llm/provider/{anthropic,openai,ollama}`.

## Decisões e pendências

- Nenhum SDK de fornecedor e nenhuma dependência nova; Bedrock sem chave de
  API (SigV4) vai pelo proxy LiteLLM, documentado.
- A revisão hoje não envia limite de resposta; `token_field` vale para todo
  chamador que envia (provado nos testes de contrato, AC-003/MUT-001).
- Modelos do OpenCode Zen servidos só em `/responses` ou `/messages` não são
  cobertos pelo perfil `opencode` (o motor fala Chat Completions).
- Nenhum provedor foi exercitado ao vivo neste card: o smoke é manual e
  depende de secrets do repositório.
- O workflow reutilizável (`.github/workflows/review.yml`) ainda exige e
  repassa só `LLM_API_KEY` e `LLM_BASE_URL`; repassar `LLM_PROVIDER` e as
  variáveis de cada perfil fica para um card com esse arquivo nos `paths`.
  Pela CLI, pela imagem e pelo servidor MCP o perfil já vale.
- `docs/agentes.md` (página dos agentes MCP) está fora dos `paths` do card: o
  OpenCode aparece em `docs/provedores.md`, que aponta para ela.
