# AUR-503 -- Command injection does not accuse a comment or prose

## Outcome

The command-injection branches AUR-486 delivered no longer accuse a
**textual mention**. A `exec.Command`, `Process.Start`,
`Invoke-Expression`/`iex` or `eval` written inside a comment (`//`, `#`,
`/* */`, `--`) or a string literal produces **no finding**, and
`eval := ...` / `eval = ...` (a declaration or assignment) produces none
either -- while the real invocation of each branch is still found.

## Measured finding (2026-09-15)

AUR-486's reviewer reproduced, in the branches AUR-486 added, the same
false-positive class AUR-486's round 2 fixed only in `sh -c`/SQL. These
lines all produced a `security/command-injection` finding before this card:

```go
// exec.Command("sh","-c","ping "+host)
// Process.Start("cmd.exe","/c ping "+host)
# Invoke-Expression "ping $host"
Write-Host "Invoke-Expression is unsafe"
# iex is dangerous
eval := compute()
```

The AUR-462 rule applies: a false positive in a merge gate teaches the team
to disable the gate.

## The fix

`internal/review/rules/security.yml` keeps every AUR-486 branch's token and
argument shape, but anchors the four affected branches to a **statement
context**: the beginning of the added line after optional whitespace, or a
statement separator (`;`, `|`, `&`). Concretely, the Go `exec.Command`, the
two C# `Process.Start` branches, PowerShell `Invoke-Expression`/`iex` and
bash `eval` each gain a leading

```
(?:^\s*|[;|&§]\s*)
```

The `^` matches the start of the per-line string the security pass matches
(`securityScanWithRules` matches each added line body individually), so a
comment marker, a `Write-Host`/`echo`/`printf` prefix, or a string-literal
assignment before the token breaks the anchor structurally -- RE2 has no
lookahead, so this is the mechanism. An optional dotted prefix
(`(?:[A-Za-z_][A-Za-z0-9_]*\.)*`) keeps `System.Diagnostics.Process.Start`
and a qualified `exec.Command` reachable without re-admitting a bare
mention. The two branches AUR-486's round 2 already anchored
(`^\s*(?:ba)?sh\s+-c` and the SQL-by-shell branch) are untouched.

bash `eval` additionally distinguishes invocation from declaration: the
branch now requires a whitespace-separated argument that is neither `:`
nor `=` (`eval\s+[^:=\s]`), so `eval "ping $1"` and `eval $cmd` still fire
while `eval := compute()` and `eval = compute()` do not.

## Acceptance

- AC-001: each branch (`exec.Command`, `Process.Start`,
  `Invoke-Expression`/`iex`, `eval`) mentioned inside a comment (`//`, `#`,
  `/* */`, `--`) or a string literal produces no finding.
- AC-002: the real invocation of each branch is still found (Go
  `exec.Command("sh","-c",...)`, C# `Process.Start` concatenation and shell
  file name, PowerShell `Invoke-Expression`/`iex`, `sh -c`/`bash -c`, and
  SQL by shell interpolation).
- AC-003: `eval := ...` / `eval = ...` produce no finding; `eval "ping $1"`
  / `eval $cmd` do.

Selectors: unit `tests/unit/AUR-503.go::TestAUR503`; integration
`tests/integration/AUR-503.go::IntegrationAUR503`; acceptance
`tests/acceptance/AUR-503.sh`, which also runs the unit and integration
bridges under `all`.

## Mutations

- MUT-001: remove the Go branch's statement guard
  (`(?:^\s*|[;|&§]\s*)(?:[A-Za-z_][A-Za-z0-9_]*\.)*\bexec\.Command` ->
  no guard). The comment mention is re-accused; if it is not, the
  mutation did not take effect and AC-001 would be a false green.
- MUT-002: over-restrict the same branch to column zero (guard -> `^`). The
  real, tab-indented Go invocation is lost; if it survives, the restriction
  did not take effect and AC-002 would be a false green.

Both are exercised by `tests/acceptance/AUR-503.sh`, each asserting a
sibling branch (bash `eval`, C# `Process.Start`) is untouched so the mutant
is proven specific rather than a blanket disablement.

## Non-goals

- No AST and no semantic analysis: the pass stays a deterministic matcher
  over the added lines.
- No existing pattern is loosened; the AUR-462/AUR-481 true positives stay
  unchanged.

## Known limitations, accepted deliberately

- **A separator inside a comment.** The statement anchor admits a token
  after `;`/`|`/`&`, so a mention whose comment reaches a separator first
  (`-- note; exec.Command(...)`) still matches. The card's AC-001 names the
  measured single-line comment and string shapes; a separator inside a
  mention is not one of them.
- **A continued block comment.** A multi-line `/* ... */` whose continuation
  line begins with the token (no marker on that line) is still anchored and
  matches. No AST/lexer means this cannot be decided line-locally.
- **An `eval` reached without a statement boundary on its own line**
  (`foo && eval $cmd` does match through `&`; a wrapper the anchor does not
  name does not). The trade is what keeps a comment/string mention from
  firing, which is this card's AC-001.

These are declared rather than silently shipped, per the card's non-goals.
