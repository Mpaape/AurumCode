# AUR-594: PR grande revisada (diff local quando a API recusa, lotes quando passa do orçamento)

## Medido antes (base e81f63c5)

- **PR #88** (intervalo `9038e70e...a7f2b0a6`, `origin/card/AUR-589`): 117
  arquivos, 1565 inserções e 30562 remoções. A API do GitHub recusa o diff
  acima de 20000 linhas com `HTTP 406` e o código `too_large`;
  `githubclient.GetPullRequestDiff` devolvia `HTTP 406: ...` como erro comum e
  `fetchPullRequest` saía 1 (`fetching pull request diff: HTTP 406 ...
  too_large`): nada revisado.
- **AUR-593** (`996732f0..8c7fcdc8`, 111 arquivos, `--base`): 6 arquivos
  ficaram fora do prompt pelo limite de tokens (prompt único de 120000) e o
  gate ficou `partial_coverage`.

## O que mudou

- **Recusa tipada** (`internal/git/githubclient/diff_too_large.go`,
  `client.go`): só `406` com `"too_large"` no corpo vira
  `ErrDiffTooLarge`; outro `406` continua erro comum. Nenhum dos dois devolve
  diff. `ParseUnifiedDiff` expõe o mesmo parser do diff da API;
  `PullRequestMetadata.BaseSHA` lê `base.sha`.
- **Diff local** (`internal/analyzer/rangediff.go`,
  `cmd/aurumcode/pr_local_diff.go`, `review_pr_inputs.go`): na recusa, o
  checkout é verificado antes de qualquer leitura (repositório e head do PR,
  `codebaseContextMismatch`; árvore limpa, `verifiedCleanCheckoutReason`). O
  head é o `HEAD` verificado; a base é `AURUMCODE_BASE_SHA` quando é um commit
  do checkout, senão `base.sha` da API. `Repo.RangeDiff` roda
  `git diff base...head` (base de merge, janelas de contexto como a API,
  `--no-ext-diff --no-textconv`, `core.fsmonitor=false`) e o texto passa por
  `ParseUnifiedDiff`: mesmos caminhos, lados e hunks do diff da API; binário
  sai sem hunk e segue a classificação de sempre do `--pr`. Sem `git`
  (`internal/analyzer/mergebase.go`, `windowed.go`): a base de merge é lida
  do banco de objetos (os ancestrais comuns que não são ancestrais de outro
  comum; zero ou mais de um, como num histórico cruzado, é erro, nunca um
  palpite) e os hunks são montados com as mesmas janelas de 3 linhas;
  `TestRangeDiffFromObjectsMatchesGit` prova arquivo a arquivo e hunk a hunk
  que o resultado é o do `git diff base...head`, inclusive com a base andando
  depois do ponto de ramificação. Base ausente ou checkout não verificado:
  saída 1, nada enviado nem publicado.
- **Parser de hunk** (`githubclient.parseHunkHeader`): o cabeçalho de um
  arquivo de uma linha apagado (`@@ -1 +0,0 @@`, que a API e o `git` emitem)
  derrubava o processo (`slice bounds out of range`); agora um lado sem
  contagem vale uma linha e um cabeçalho malformado dá zeros
  (`TestParseHunkHeaderWithoutCount`).
- **Diff local sempre?** Avaliado e recusado: a CLI direta e os testes com
  GitHub falso não têm checkout verificado, então "sempre local" trocaria uma
  revisão que hoje funciona por uma falha; e com a API respondendo, o diff dela
  é a fonte que o PR mostra. O local é só o caminho da recusa por tamanho.
- **Lotes** (`internal/review/batches.go`, `batch_merge.go`,
  `reviewer.go`): `GenerateReviewWithContext` monta o prompt único como antes;
  só quando ele deixaria um arquivo com patch omitido ou parcial (arquivo sem
  patch não conta) a revisão planeja lotes: arquivos agrupados por diretório,
  diretório inteiro num lote quando cabe, senão o lote é completado arquivo a
  arquivo; arquivo grande demais sozinho é um lote próprio (parcial,
  declarado). Cada lote passa pelas mesmas quatro etapas (`reviewPrepared`)
  com a evidência dos seus arquivos (ids atribuídos uma vez, os mesmos em
  todos os lotes). Os resultados são consolidados: listas concatenadas,
  contagens somadas, avisos juntados, flag ligada continua ligada, veredito
  mais severo; um gate. Transcrições de deliberação são somadas. Um lote que
  falha faz a revisão falhar. O prompt único que cabe fica byte a byte igual.
- **Tetos** (`internal/prompt/templates/limits.yml`: `batch_max_count: 4`,
  `batch_max_prompt_tokens: 480000`; `internal/config/batches.go`: seção
  `batches` com `max_batches` e `max_prompt_tokens`, validada, linha em
  `governedSections`, política decide sozinha). A partir do primeiro lote
  que passa de um teto, nenhum lote é revisado: os arquivos vão para
  `code_files_omitted` e `code_files_omitted_paths`, o aviso de cobertura os
  lista (`passes.go`, `review_coverage.go`), a auditoria os põe em
  `coverage.omitted_files`, e a cobertura parcial retém a aprovação.
- **Auditoria** (`internal/render/audit.go`, `cmd/aurumcode/review_batches.go`,
  `compliance_artifacts.go`, `review_evidence.go`): campo `batches` (índice,
  arquivos, tokens estimados); stderr `reviewed in N batches by directory
  (files per batch: ...)`.
- **Tutorial** `revisao`, caso `pr-workflow`: GitHub falso (`_lib/github-falso.py`
  aceita `406` e `BASE`; `_lib/pr.sh` ganha `tut_pr_servidor_recusa`) com
  três passos: 406 + diff local + 3 lotes (exit 0, APPROVE); teto
  `batches.max_batches: 1` (exit 1, `partial_coverage`, 4 arquivos listados);
  checkout sujo (exit 1, nada publicado). O caso ficou dentro de
  `pr-workflow` (um caso novo exigiria registro em `docs/specs/AUR-561.md`,
  fora de `paths`).
- **Docs**: `configuration.md` (seção "PR grande" e tabela), `getting-started.md`,
  `architecture.md`, `tutorials/revisao.md`.

## Decisões e pendências

- O caso do PR grande vive dentro de `pr-workflow` do tutorial `revisao`: um
  caso novo exigiria registro em `docs/specs/AUR-561.md`, fora de `paths`.
- `runProfilePasses` (com `review.profiles`) monta revisores com os tetos
  padrão: a seção `batches` não chega a eles.
- Um `max_prompt_tokens` menor que um prompt revisa zero lotes: a revisão
  fica parcial e a aprovação é retida, mas o stderr diz "reviewed in 0
  batches".

- O aviso de cobertura dos arquivos fora pelo teto reaproveita a frase "left
  out of the review by the token budget" (o teto de lotes é orçamento de
  tokens); a lista nomeia cada arquivo.
- `deliberation.max_cost_tokens` e `--limite` valem por lote: uma revisão em
  quatro lotes pode gastar até quatro vezes o teto de deliberação.
- O veredito reaproveitado (`verdict-reuse`) não inclui os tetos de lotes na
  chave: uma revisão completa é a mesma com qualquer teto, e uma parcial não é
  reaproveitada.
