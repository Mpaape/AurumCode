# AUR-595: a autorrevisão conclui em PR real

## Medido antes (base 7b9cb359, PR #89)

A autorrevisão da PR #89 (configuração do próprio repositório, AUR-591)
terminou inconclusiva por três motivos. Auditoria do job
(`aurumcode-audit-89`): `deliberation.rounds=1`, `tokens_in=65918`,
`tokens_out=91`, desfecho `deliberation_limit:max_cost_tokens`; gate
`fail` com `SECRETS (gitleaks, ...) inconclusivo (secrets_execution_error)`
e dois `security/command-injection` em
`demo/tutoriais/sast/out/nosemgrep-e-semgrepignore.log:36` e
`demo/tutoriais/sast/out/regra-local.log:22`.

1. **Teto de deliberação contava o prompt base.** `Session.Run`
   (`internal/deliberation/session.go`) somava `TokensIn + TokensOut` de
   todas as rodadas e comparava com `max_cost_tokens` (60000). A primeira
   rodada já carrega o prompt base inteiro (65918 tokens numa PR média):
   o teto estourava antes de o modelo pedir qualquer ferramenta.
2. **Gitleaks no merge commit.** Diagnóstico reproduzindo o job: clone com o
   mesmo fetch do `actions/checkout` (`fetch-depth: 0`:
   `+refs/heads/*:refs/remotes/origin/*` e tags), checkout destacado da
   cabeça da PR, montado só leitura num container root com
   `safe.directory` via `GIT_CONFIG_*`, e os mesmos comandos de
   `verifyRange`/`scanRange`:

   ```text
   == GITHUB_SHA=a1ee8f28... (refs/pull/89/merge)
   cat-file 098f7342... rc=0
   fatal: Not a valid object name a1ee8f28...^{commit}
   cat-file a1ee8f28... rc=128          -> ErrBadRange -> secrets_execution_error
   == GITHUB_SHA=110ffb72... (cabeça da PR)
   cat-file 110ffb72... rc=0
   gitleaks rc=0  INF 12 commits scanned.  WRN leaks found: 2
   ```

   O `env:` do passo define `GITHUB_SHA` com a cabeça, mas num evento
   `pull_request` o GitHub reserva a variável ao merge commit sintético
   (o mesmo fato de AUR-504; o `workflow_sha` da auditoria é o merge
   `a1ee8f28`). O checkout da cabeça não traz `refs/pull/N/merge`, então a
   ponta do intervalo não existia no clone. O motivo publicado era só o
   token, sem dizer qual ponta faltava.
3. **Logs gravados de tutorial na revisão.** `demo/tutoriais/*/out/*.log`
   repetem de propósito exemplos com `eval()`; o passe de segurança os
   acusou como código adicionado.

## O que mudou

- `internal/deliberation/transcript.go`, `session.go`: o transcript registra
  `base_tokens` (entrada da primeira rodada, o prompt base como o provedor o
  mede) e `cost_tokens` (saída de cada rodada + o que a entrada de cada
  rodada seguinte traz além do prompt base). `max_cost_tokens` limita
  `cost_tokens`; o prompt base segue sob o orçamento do prompt. O detalhe do
  limite diz os dois números.
- `cmd/aurumcode/pr_scan_range.go`, `review_pr_analysis.go`: no `--pr` o
  intervalo dos scanners é `AURUMCODE_BASE_SHA..HEAD do checkout verificado`
  (o `HEAD` que `resolveCheckout` já provou igual à cabeça da API); nunca
  `GITHUB_SHA`. Sem checkout verificado a cabeça fica vazia e os scanners
  continuam bloqueados (`*_unverified_checkout`).
- `internal/scanner/detail.go`, `executor.go`: `Outcome.Detail` é o erro da
  engine numa linha (espaços colapsados, até 240 bytes, corte em fronteira
  de rune). `internal/gate/scanner.go`: `Scan.Detail`; a linha do gate fica
  `inconclusivo (<token>) [detalhe: ...]` (o token continua inteiro entre
  parênteses). `cmd/aurumcode/scanner_pass.go`: o detalhe passa pelo filtro
  de redação da revisão antes de qualquer saída e entra na limitação
  publicada (`notice.scanner_detail`, `internal/i18n/catalog.yml`).
- `internal/scanner/gitleaks/invocation.go`: os erros dizem qual ponta
  (`base commit <id> not found in the checkout`), clone raso, e a última
  linha de stderr do `git`/`gitleaks` que falhou (ou a primeira linha
  `ERR`/`FTL` de um log com erro e exit 0).
- `.aurumcode/config.yml`: `ignore` ganha `demo/tutoriais/*/out/**` e
  `demo/tutoriais/*/expected/**`. `docs/configuration.md`: teto relativo,
  intervalo do `--pr`, detalhe do motivo, recomendação para artefatos
  gerados. `docs/getting-started.md`: as três notas.

## AC-004: como verificar na PR deste card

O `--pr` lê do **branch base** as configurações que afetam o gate (regras,
`ignore`): a PR não enfraquece a própria revisão. Logo o `ignore` novo de
`.aurumcode/config.yml` só vale para as PRs abertas depois de este card estar
no `main`; o código (teto relativo, intervalo, detalhe) vale já, porque o
workflow roda a ferramenta do merge da PR (`job.workflow_sha`).

1. Abrir a PR de `card/AUR-595` para `main`.
2. O check `review / Review pull request` precisa terminar verde, com o
   `aurumcode/policy-gate` em success. Na auditoria (`aurumcode-audit-<N>`):
   `deliberation.outcome` diferente de `deliberation_limit:*`,
   `deliberation.base_tokens` e `cost_tokens` presentes, nenhum
   `secrets_execution_error` em `gate.reason`.
3. Se o passe de segurança acusar `demo/tutoriais/*/out/*.log` ou
   `expected/*.txt` regravados por este card (o `ignore` ainda é o do
   `main`), não é regra a desligar: o hunk de `.aurumcode/config.yml` entra
   no `main` primeiro e a PR é reavaliada por um novo evento (`git merge
   main` + push), que relê a configuração da nova base.

## Fora do escopo

Desligar regra, aumentar tetos, tratar falha de scanner como sucesso. Os
achados do gitleaks na PR #89 são dela.
