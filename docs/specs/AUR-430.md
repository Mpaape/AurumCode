# AUR-430: `aurumcode review`

Restores AurumCode's local code-review engine (deleted 2025-11-03, commit
`c12d7ab` is the last commit before deletion) and wires it behind a new
CLI entrypoint, `cmd/aurumcode`.

## Command

```
aurumcode review --base <ref>
```

Run from inside the git repository you want reviewed (bare or a normal
working tree with a `.git` directory). It diffs `<ref>` against `HEAD` in
that repository, sends the diff to a model, and prints every finding the
model reports as one line per finding:

```
<file>:<line>: [<severity>] <message>
```

sorted by `(file, line)` so the same input always prints in the same order.
If the model reports no findings, it prints `No issues found.`. Running the
command twice against the same input always produces byte-identical output.

### Flags

| Flag | Required | Meaning |
|---|---|---|
| `--base <ref>` | yes | The ref to diff against `HEAD`. Accepts a 40-hex commit SHA, a branch name (resolved under `refs/heads/`), `HEAD`, or any of those with a `~N` parent-walk suffix (`HEAD~1`, `main~2`, ...). |

### Exit codes

| Code | Meaning |
|---|---|
| `0` | The command ran and printed its findings (including zero findings). |
| `1` | A real failure: not a git repository, the ref does not resolve, the LLM call failed, or the model's response could not be understood at all (see "Parser fallback" below). |
| `2` | Usage error: unknown subcommand, or `review` invoked without `--base`. |

### Provider configuration

`aurumcode review` never hardcodes a vendor. It selects a provider from the
environment, in this order:

1. **`AURUMCODE_LLM_FIXTURE=<path>`** — read that file's content and return
   it verbatim as the model's response. This is how the acceptance test and
   the example below run fully offline and deterministically; it is not a
   special case in the review engine, just an `llm.Provider` implementation
   (`internal/review.FakeProvider`) like any other.
2. **`LLM_API_KEY` and `LLM_BASE_URL`** — use the existing OpenAI-compatible
   LiteLLM proxy provider (`internal/llm/provider/litellm`), the same one
   `cmd/regenerate-docs` already uses, naming a model via `LLM_MODEL`
   (default `gpt-4`).
3. Neither set: the command fails with a clear error naming both options,
   never a panic or a silent no-op provider.

### Example (no secrets)

```console
$ cd tests/fixtures/repos/git-demo/repo.git   # a deterministic fixture repo
$ AURUMCODE_LLM_FIXTURE=../../review/known-problem-response.json \
    go run ../../../../../cmd/aurumcode review --base HEAD~1
config/demo-tokens.txt:4: [error] A credential-shaped value was committed in plain text (DEMO_API_TOKEN).
```

The fixture response and the values it describes
(`AURUM-FAKE-TOKEN-0000-0001` and friends) are synthetic; see
`tests/fixtures/repos/git-demo/content/03/config/demo-tokens.txt`.

### Diagnosing a failure

| Symptom | Likely cause |
|---|---|
| `aurumcode review: <dir> is not a git repository` | `cwd` has no `.git` directory and is not itself a bare repository (no `HEAD`/`objects`/`refs`). |
| `aurumcode review: computing diff <ref>..HEAD: ...object ... not found as a loose object (packed objects are not supported by this reader)` | The repository has been `git gc`'d and its objects live in a packfile; see "Scope" below. |
| `aurumcode review: no LLM provider configured: ...` | Neither `AURUMCODE_LLM_FIXTURE` nor `LLM_API_KEY`+`LLM_BASE_URL` is set. |
| `aurumcode review: could not understand the model's response (no_json_found\|invalid_json\|validation_failed\|no_findings_recovered)` | The model's response had neither valid JSON nor a recognizable degraded-mode finding line (see below). |

## Design decisions

### Why there is no `git` subprocess

The card's sealed acceptance profile, `bootstrap-readonly-v1`, carries a Go
toolchain and bash but **no `git` binary**, network access denied. Shelling
out to `git diff` (a natural first design, and the one this card's own text
names) is therefore not viable inside the only environment that gates this
card — the same fact card AUR-011's acceptance program documents and
independently relies on for the same fixture.

`internal/analyzer/gitrepo.go` instead reads git's on-disk object format
directly: it resolves `HEAD`/`HEAD~N`/branch refs by reading loose ref
files, inflates loose objects (`zlib` + the standard `type size\0content`
header), and walks commit → tree → blob to build the diff itself, using a
from-scratch Myers `O(ND)` line diff (`internal/analyzer/textdiff.go`) for
each changed blob. This is a deliberate, documented scope narrowing, not a
silent one:

- **Supported**: loose objects, the format every fresh commit (and the
  `tests/fixtures/repos/git-demo` fixture) uses.
- **Not supported**: packfiles (`git gc`'d repositories). Reading a packed
  object returns a clear, typed error naming the object and the reason,
  never a silently empty diff.

### Prompt sourced from `.aurumcode/prompts/review.md`

`internal/prompt/templates/review.md` is a build-time copy of the read-only
`.aurumcode/prompts/review.md`. `go:embed` patterns cannot reach outside
their own source file's directory tree, so a runtime read of the read-only
path was the only alternative — but that would tie the binary's behavior to
running with a particular working directory or a repo-relative env var,
which a CLI meant to review an arbitrary target repository should not
require. Baking the content in at build time keeps the binary self-contained
regardless of where it runs, at the cost of the copy needing to be refreshed
if `.aurumcode/prompts/review.md` changes (out of this card's scope to
automate).

### Parser fallback

The restored `internal/prompt.ResponseParser.ParseReviewResponse` used to
have exactly one path: parse the model's response as JSON, or fail the
entire review with no output. That is a real usability problem for smaller
or local models that cannot reliably follow a JSON schema.

`ParseReviewResponse` now has two paths:

1. **JSON** (unchanged behavior for a well-formed response): extract JSON
   from a fenced code block or a bare `{...}`, repair common malformations
   (see `repairJSON` below), decode and validate it.
2. **Degraded fallback**: if step 1 fails for any reason, scan the response
   line by line for the convention

   ```
   [-*] <path>:<line>: [severity:] <message>
   ```

   (severity defaults to `warning` when omitted) and turn every match into a
   `types.ReviewIssue`. If that recovers at least one finding, it is
   returned as a normal, successful result with
   `Metadata["parse_mode"] == "degraded"`.

If **neither** path produces anything, `ParseReviewResponse` returns a typed
`*prompt.ParseError` (with a `Kind` — `no_json_found`, `invalid_json`,
`validation_failed`, or `no_findings_recovered` — and a bounded preview of
the raw response) rather than an empty-but-successful result. This
distinction matters: an empty `[]ReviewIssue` must always mean "the model
looked and found nothing," never "the engine gave up and said nothing."

### `repairJSON`: quotes are repaired, not blindly swapped

The restored `repairJSON` translated typographic ("smart") double quotes
(`“` `”`) to straight ASCII quotes with a global string
replace over the *entire* response, including inside already-open JSON
string values. That is a real bug: substituting inside a string value
inserts a bare, unescaped `"` that ends the string early and corrupts
everything after it.

`repairJSON` now tracks, character by character, whether it is currently
inside a JSON string. A quote character — straight or typographic — only
closes the current string when it looks like a genuine boundary (the next
non-whitespace character is one of `, } ] :`, or end of input); any other
quote met inside a string is escaped in place instead. Typographic single
quotes/apostrophes (`‘` `’`) are never JSON delimiters, so they are still
normalized with a plain global replace. See
`TestRepairJSON/smart_quotes` and
`TestRepairJSON_TypographicQuotesInsideStringsDoNotCorruptJSON` in
`internal/prompt/parser_test.go`.

### `ISOScores` is optional

`pkg/types.ReviewResult.ISOScores` is `*ISOScores` today (the restored
`c12d7ab` code treated it as a value field). This card's engine never asks a
model to score ISO/IEC 25010 characteristics — that scoring pipeline
(`internal/review/rules.go`, `internal/review/iso25010`) is explicitly out
of scope here and belongs to dependent cards — so a response that omits
`iso_scores` is valid and `ISOScores` stays `nil`; a block that is present
is still validated to the 1–10 range.

### No vendor coupling

`internal/analyzer`, `internal/prompt` and `internal/review` name no LLM
vendor anywhere. The engine's only contact point with a model is
`internal/llm.Orchestrator.Complete(ctx, prompt, llm.Options)`, called with
whatever `llm.Provider` `cmd/aurumcode`'s `selectProvider` constructed —
`internal/review.FakeProvider` for the offline/fixture path, or the
existing vendor-neutral `internal/llm/provider/litellm.Provider` for a live
one. `internal/review/reviewer_test.go`, `tests/unit/AUR-430.go`,
`tests/integration/AUR-430.go` and the acceptance program all run the real
review pipeline through `FakeProvider` and never touch a vendor package;
that is the proof, not just the claim, that the pipeline is
provider-agnostic.

## Out of scope (see the card)

- Fetching a PR's diff from a Git host (GitHub, etc.) or publishing a
  review comment — future cards (AUR-437+).
- Rule citation (`internal/review/rules.go`) and ISO/IEC 25010 scoring
  (`internal/review/iso25010`) — dependent cards.
