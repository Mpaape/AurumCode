01

DO REPOSITÓRIO AO PRIMEIRO PARECER

Instale uma vez.

A

Conecte o modelo

Em Settings → Secrets and variables → Actions do repositório que receberá o review, adicione dois secrets.

LLM_BASE_URL
URL base do serviço compatível com OpenAI, incluindo /v1 quando exigido.
LLM_API_KEY
A credencial desse serviço. Nunca coloque seu valor no YAML.
B

Adicione o workflow

Salve o arquivo abaixo em .github/workflows/aurumcode.yml. Ele acompanha a branch publicada main.

Se o endpoint exigir um nome de modelo, crie a variável de Actions LLM_MODEL. Caso contrário, deixe-a vazia para usar o default do serviço.

C

Abra um PR com código

Integre o workflow e a configuração na branch base. Depois abra um PR com uma pequena mudança de comportamento e veja o resultado na aba Conversation.

Novos commits do PR acionam as execuções seguintes.

.github/workflows/aurumcode.yml

O workflow usa o token do próprio GitHub para publicar. Secrets não ficam disponíveis em PRs de forks por padrão. Esses PRs precisam de um fluxo confiável separado; não execute código de forks com secrets.

02

SÓ O QUE PRECISA MUDAR

Faça o review do seu jeito.

O arquivo de configuração é opcional. Escolha abaixo e copie apenas as preferências diferentes dos defaults: inglês, comentários e sem comentários nas linhas.

Tudo é gerado no seu navegador. Nenhuma credencial é solicitada ou enviada.

.aurumcode/config.yml
review:
  language: pt-BR
  publication: review
  inline_comments: true

O review formal pode solicitar mudanças quando há achados bloqueantes.

Para acompanhar sem bloquear o merge, não marque o status do AurumCode como obrigatório nas regras da branch. Comentários, review formal e status de commit têm funções diferentes.

03

O CONHECIMENTO DO SEU TIME

Contexto muda o parecer.

Comece com .aurumcode/prompt.md. Esse arquivo é encontrado automaticamente e acrescenta orientações ao review. Escreva contratos do domínio e prioridades reais do time.

.aurumcode/prompt.md
Revise primeiro correção e compatibilidade dos contratos públicos.
Valores monetários são armazenados em centavos inteiros.
Operações de pagamento devem preservar a chave de idempotência.
Use o código e os testes disponíveis para justificar cada achado.
Sugira código apenas quando a substituição for local e segura.
Se faltar contexto para demonstrar um problema, indique a limitação.
Expandir com skills e documentos do projeto

Uma skill é um Markdown com orientações reutilizáveis. Liste arquivos que ajudem a interpretar o domínio; eles precisam existir na branch base.

.aurumcode/config.yml
review:
  language: pt-BR
  context:
    skills:
      - .aurumcode/skills/backend.md
    docs:
      - docs/architecture.md

O prompt padrão continua ativo. Para usar outro caminho, adicione context.prompt. Skills são orientações textuais: elas não instalam ferramentas nem executam scripts.

O contexto acompanha o código, não amplia a cobrança.

Contratos e testes ajudam o raciocínio. Achados apontam para a adição ou remoção que causa o problema, com evidência, impacto e verificação. A presença desses campos não prova automaticamente que a conclusão está certa.

No PR, o agente também recebe as reviews, comentários e respostas anteriores do GitHub, sem configuração extra. Esse conteúdo é enviado ao endpoint LLM configurado, após remoção de segredos reconhecidos. O histórico ajuda a considerar correções e contestações; ainda não há revisão incremental, resolução de threads ou garantia de não repetir apontamentos.

NA CONVERSA DO TIME

Um parecer que dá para usar.

01 / ENTENDER

Resumo e pontos fortes

O comportamento alterado e os benefícios concretos encontrados no código. Elogios são opcionais; o agente não precisa preencher espaço.

02 / CORRIGIR

Problemas acionáveis

Localização, impacto, evidência, correção sugerida e como verificar. Um achado grave pode produzir um request changes no review formal.

03 / MELHORAR

Sugestões com parcimônia

Melhorias opcionais, locais e justificadas. Quando há uma substituição elegível, o GitHub oferece aplicar a sugestão. O autor decide.

04 / CONFERIR

CI e próximos testes

O workflow reutilizável envia os estados dos checks. Sem logs suficientes, o agente deve indicar o diagnóstico necessário, sem inventar a causa.

TAMBÉM NO TERMINAL

Use com Docker.

Construa a imagem a partir do checkout do AurumCode. Depois execute no repositório que deseja revisar, exportando as credenciais no terminal. Nenhuma instalação de Go no host é necessária.

Terminal
docker build -t aurumcode:local /caminho/para/AurumCode

# Execute dentro do repositório a revisar.
docker run --rm \
  -v "$PWD:/workspace:ro" -w /workspace \
  -e LLM_API_KEY -e LLM_BASE_URL -e LLM_MODEL \
  aurumcode:local review --base HEAD~1

--base compara commits com HEAD; não inclui mudanças ainda não commitadas. A saída local é uma lista de achados; o parecer estruturado é publicado no PR. Use review --help para as opções.

QUANDO ALGO NÃO ENCAIXA

Respostas diretas.

Qual modelo devo configurar?

Use um modelo de revisão de código disponível no seu endpoint. AurumCode não escolhe um modelo por você. A variável LLM_MODEL passa o identificador exato; sem ela, o serviço precisa oferecer um default.

Configurei português, mas o resultado não mudou.

Confira review.language: pt-BR em .aurumcode/config.yml. O idioma pode ser lido do PR; prompts, skills e preferências que afetam a revisão vêm da branch base. Integre esses arquivos antes de testar o próximo PR.

O job falhou e não houve comentário.

Abra o log da etapa de review. Erros de autenticação pedem conferir os secrets; 404 de modelo/endpoint pedem conferir a URL e LLM_MODEL; 403 na publicação pede conferir pull-requests: write e a política do repositório. Falhas anteriores à publicação não garantem um comentário no PR.

O CI falhou. O AurumCode explica a causa?

Ele recebe nome, estado e link dos checks pelo workflow reutilizável. Isso permite mencionar a falha, mas nem sempre explica sua causa. Logs de erro ou saída dos testes precisam ser fornecidos como contexto para um diagnóstico fundamentado.

Qual a diferença entre review, comentário e check?

Review usa a revisão formal do GitHub, inclusive pedido de mudanças quando aplicável. Comentário publica na conversa sem um voto formal. Check aqui é um status de commit: o workflow reutilizável o publica; o merge só fica bloqueado se a regra da branch o exigir.

Meus prompts conseguem desligar regras?

Prompts, skills e docs orientam a análise, mas não mudam permissões nem desativam a proteção de segredos. Ignorar caminhos ou alterar regras exige configuração explícita; veja a referência no repositório.

ESCOPO ATUAL DO PRODUTO

O que está disponível hoje.

Disponível

  • Revisão por LLM do diff e contexto fornecido.
  • Histórico de reviews e respostas do próprio PR.
  • Idioma, prompts, skills e docs configuráveis.
  • Comentários, reviews formais e sugestões inline.
  • CLI e núcleo de revisão escritos em Go.
  • Execução via Docker e GitHub Actions.

Ainda não implementado

  • Revisão incremental e gestão de pendências entre rodadas.
  • Navegação autônoma por todo o repositório.
  • Busca web ou execução de ferramentas pelo modelo.
  • Verificação automática da veracidade de cada achado.
  • Garantia de parecer idêntico ao repetir o review.

O limite de resposta fica a cargo do modelo e do serviço. Isso não significa contexto infinito: há restrições de arquivos e contribuições, e erros ou omissões precisam ser conferidos nos diagnósticos do job.
