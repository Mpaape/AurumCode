As 4 regras de segurança com matcher determinístico

O catálogo embutido (internal/review/rules/security.yml) tem 8 regras nomeadas, mas só 4 comparam a linha adicionada contra uma expressão regular; as outras 4 são metadado citável pelo modelo, nunca aplicado pelo passe determinístico.

  • security/sql-injection — string com verbo SQL concatenada por + a um identificador (ou format! em Rust).
  • security/xss — atribuição direta a innerHTML/outerHTML, document.write(...) ou dangerouslySetInnerHTML a partir de um identificador, sem chamada no meio.
  • security/command-injection — chamada de shell (system, exec/execSync, subprocess.*, spawn(...,shell:true), Command::new("sh").arg("-c")) com argumento concatenado.
  • security/hardcoded-secret — atribuição de uma string a um nome que contém key/secret/password/token/credential, com mistura de letra e número.

As demais 4 (path-traversal, weak-crypto, insecure-random, missing-auth) ficam sem matcher por decisão deliberada: decidir sem seguir o dado exigiria análise de fluxo que uma regra por linha não sustenta.

Disponível hoje

  • Revisão por LLM do diff e do contexto fornecido, quando há provedor configurado.
  • Análise estática determinística sempre ativa (segredo, SQL, command injection, permissão de arquivo) mais o passe opcional --seguranca.
  • Contexto de codebase limitado por heurística, não por índice completo do repositório.
  • Histórico de reviews e comentários do próprio PR, incluído sem configuração extra.
  • Resumo TL;DR e diagrama Mermaid do fluxo alterado.
  • Proposta determinística de casos de teste no parecer.
  • Memória de revisão opcional entre execuções (review.memory).
  • Comentários, review formal e sugestões inline; aurumcode fix para aplicar fora do GitHub.
  • Estimativa e teto de custo (--limite) antes de chamar o modelo.
  • Execução via Docker e via GitHub Actions; CLI e núcleo em Go.

Limites atuais

  • Revisão incremental: cada execução reavalia o PR inteiro, sem lembrar pendências resolvidas entre rodadas.
  • Execução automática, no CI, dos casos de teste propostos em sandbox.
  • Navegação autônoma por todo o repositório além da heurística de contexto atual.
  • Busca web ou execução de ferramentas externas pelo modelo.
  • Verificação automática da veracidade de um achado do modelo.
  • Garantia de parecer idêntico ao repetir a mesma revisão.

Em um runner efêmero do GitHub Actions, review.memory: local não sobrevive sozinho entre execuções — persistir exige cachear o diretório entre jobs; ephemeral nunca persiste, por definição.

COMO USAR CADA RECURSO

Ativa, funciona, exemplo

Sem provedor configurado, só o baseline determinístico roda. Com provedor, cada capacidade abaixo consome tokens do seu modelo — cada card marca o que é padrão, o que é opcional e o que custa.

Análise determinística ligado por padrão

  1. Ativa

    A base já roda em todo review de PR, sem configurar nada: segredo, SQL, command injection e permissão de arquivo. O passe --seguranca soma o matcher de XSS — já ativo por padrão no workflow reutilizável (security: true), opcional na CLI local.

  2. Como funciona

    Cada linha adicionada passa por matchers determinísticos. O catálogo de segurança tem 8 regras nomeadas, mas só 4 têm matcher — as outras 4 ficam como metadado citável pelo modelo, nunca aplicado pelo passe determinístico. Sem modelo, sem custo de LLM.

  3. Exemplo
    aurumcode review --base HEAD~1 --seguranca

Resumo + diagrama ligado por padrão

  1. Ativa

    Já roda em todo review com provedor, sem flag e sem arquivo.

  2. Como funciona

    O modelo resume a mudança (TL;DR) e desenha o fluxo alterado em Mermaid, direto do diff. Entra no custo de tokens do seu provedor.

  3. Exemplo

    Nada para copiar — aparece no comentário do PR.

Contexto de codebase ligado por padrão

  1. Ativa

    Já roda por heurística: arquivos próximos ao diff entram no prompt, sem índice do repositório.

  2. Como funciona

    O parecer pode apontar efeitos além do diff isolado. Aumenta tokens — para direcionar, liste arquivos em review.context.

  3. Exemplo
    # .aurumcode/config.yml
review:
  context:
    skills:
      - .aurumcode/skills/backend.md
    docs:
      - docs/architecture.md

Sugestão de 1 clique opcional

  1. Ativa

    Desligado por padrão. Ative no workflow (inline_comments: true) ou no .aurumcode/config.yml.

  2. Como funciona

    Achados elegíveis viram comentários na linha alterada; no review formal, o GitHub oferece aplicar a substituição — o autor decide. Redigir cada sugestão consome tokens.

  3. Exemplo
    # .aurumcode/config.yml
review:
  inline_comments: true

Memória por repositório opcional

  1. Ativa

    Desligado por padrão (off). Ative com review.memory: local no .aurumcode/config.yml.

  2. Como funciona

    Guarda observações de revisões anteriores no cache para reduzir repetição — nunca muda regras, severidade ou veredito. Em runner efêmero, cacheie o diretório entre jobs.

  3. Exemplo
    # .aurumcode/config.yml
review:
  memory: local

Fix por CLI CLI local

  1. Ativa

    Fora do GitHub, na sua máquina: o binário local lê a revisão publicada e gera o patch.

  2. Como funciona

    aurumcode fix converte as sugestões da revisão em um diff unificado aplicável. Você inspeciona e aplica; nada é escrito no repositório sozinho.

  3. Exemplo
    docker run aurumcode:local fix < review-response.json > fix.patch
git apply --check fix.patch

Custo sob controle opcional

  1. Ativa

    Sem teto por padrão. Defina o teto em dólar com --limite na execução local.

  2. Como funciona

    O comando estima o custo antes de chamar o modelo; se a estimativa passar do teto, recusa — sem gastar nada.

  3. Exemplo
    docker run aurumcode:local review --base HEAD~1 --limite 0.50

Modelo agnóstico opcional

  1. Ativa

    Sem LLM_MODEL, o serviço escolhe o modelo dele. Defina o endpoint com variáveis de ambiente.

  2. Como funciona

    Qualquer endpoint compatível com OpenAI, inclusive local. O nome do modelo entra no cálculo de custo junto com --limite.

  3. Exemplo
    export LLM_BASE_URL=http://127.0.0.1:8080/v1
export LLM_API_KEY=your-api-key
export LLM_MODEL=your-model

DO ZERO AO PRIMEIRO REVIEW

O próximo review
começa aqui.

Cole este arquivo na branch base e adicione os dois secrets do provedor. O AurumCode é software livre (MIT), sem assinatura. O uso do seu provedor de LLM e do GitHub Actions pode ter custo.

.github/workflows/aurumcode.yml
name: Code review
on:
  pull_request:
    types: [opened, synchronize, reopened]
permissions:
  contents: read
  pull-requests: write
  statuses: write
  checks: read
jobs:
  review:
    uses: Mpaape/AurumCode/.github/workflows/review.yml@v2
    with:
      model: ${{ vars.LLM_MODEL }}
    secrets:
      LLM_API_KEY: ${{ secrets.LLM_API_KEY }}
      LLM_BASE_URL: ${{ secrets.LLM_BASE_URL }}

Adicione contexto do seu repositório

Os caminhos abaixo são exemplos: crie os arquivos ou use caminhos existentes. Contexto informa a revisão; não aprova mudanças.

review:
  context:
    prompt: docs/review-guidance.md
    skills:
      - docs/review-skills.md
    docs:
      - docs/architecture.md

Em Settings → Secrets and variables → Actions, adicione LLM_API_KEY e LLM_BASE_URL do seu endpoint compatível com OpenAI; LLM_MODEL é opcional, use se o serviço exigir um nome de modelo. Secrets do repositório não ficam disponíveis em PRs de fork por padrão — não execute código de fork com eles.
