    AUR-519: skill vira gate, com bloqueio e inconclusivo configuráveis

    Contrato

    A análise do gate é feita pelo que uma skill Markdown diz, não por regra escrita em Go. Toda seção ## de toda skill (as da política central e as do próprio repositório) é lida a cada execução e vira uma regra citável: <arquivo-base-da-skill>#<slug-da-seção>. A política (nunca o repositório sozinho, a menos que ele opte) declara, em gate.fail_on, quais severidades reprovam o check, e em gate.inconclusive, o que uma revisão inconclusiva faz (block ou warn). Ver docs/configuration.md's "Gate" section para a sintaxe completa.

    Estado desta entrega

    O mecanismo está implementado e ligado de ponta a ponta em --base (runReview) e --pr (runPRReview), com testes de comportamento reais pelo comando (não só unitários) para AC-001 a AC-008 — incluindo o caminho multi-perfil (--perfis): runProfilePasses (cmd/aurumcode/profiles.go) instala o mesmo catálogo dinâmico e o mesmo catálogo de rule_id fundido em CADA Reviewer que constrói, um por perfil, para que selecionar --perfis nunca narrowe o gate de volta ao catálogo embutido sozinho.

    Correções de uma revisão independente (B1-B6)

    Uma revisão independente do commit 472f56b encontrou 5 defeitos reais, todos corrigidos nesta entrega, cada um com um teste de regressão que falha sem o fix (confirmado por mutação manual em B1 e B3):

    • B1 evaluateGate retornava assim que inconclusiveReason era não-vazio, para QUALQUER modo (inclusive warn), pulando o loop de limiar de severidade por completo -- uma quebra de severidade real, presente ao lado de uma cobertura parcial forçada (ex.: um arquivo ignorado/oversized no mesmo PR), saía com exit 0. Corrigido: só block retorna antes do loop; warn e a ausência da chave inconclusive marcam Inconclusive e continuam para o loop, e uma quebra real sempre marca Fail e o novo campo Breach. Breach separa "falhou porque o bloqueio de inconclusivo disparou, sem nunca checar achados" de "falhou porque um achado real cruzou o limiar", para o switch do status publicado e para o código de saída (Breach → exitFindings sempre, Fail sem Breach → exitQualityNotReviewed).
    • B4 o limiar comparava só issue.Severity -- a severidade que o próprio modelo devolveu, sob o controle do diff que ele está revisando (uma linha de injeção de prompt poderia pedir para rebaixar a severidade e escapar do gate). effectiveSeverityRank agora usa o MAIOR rank entre issue.Severity e a severidade que a própria regra dinâmica declarou (review.Rule.Severity, a linha opcional severity: da seção da skill) -- a declaração do autor da política/skill age como piso que o modelo não controla.
    • B5 com gate.fail_on configurado e gate.inconclusive ausente, uma revisão inconclusiva publicava "gate de política aprovado". Corrigido pelo mesmo fix de B1: ausência de inconclusive se comporta como warn -- nunca "aprovado", nunca bloqueia por si só.
    • B2 runProfilePasses nunca copiava Metadata de cada passe de perfil para o resultado combinado, então prompt.IsDegradedParse(merged) era sempre falso sob --perfis, por mais que um perfil tenha degradado. Corrigido: se QUALQUER perfil degradou, o combinado carrega ParseModeKey=ParseModeDegraded (escrito pelo motor, nunca copiado de um mapa que o modelo controla); os contadores de cobertura do AUR-476 são preservados do primeiro perfil (são os mesmos para todos, mesmo diff/orçamento).
    • B3 persistFreshResults cacheava um parse degradado (ou uma cobertura parcial) como "zero achados" -- uma segunda execução contra a MESMA fixture (a chave de cache já incorpora o conteúdo do arquivo de fixture) lia do cache um resultado "limpo" sem nenhum sinal de degradação, e um gate configurado passava com exit 0 na repetição. Corrigido: o cache nunca persiste quando prompt.IsDegradedParse(result) ou a cobertura é parcial.
    • Também corrigido (não um defeito B1-B5, apontado na mesma revisão): o motivo "provider_failure" do --pr estava rotulado errado para uma falha de PARSE (qualityDegraded: o provedor respondeu, o JSON é que era inválido) -- renomeado para "model_parse_failure".
    • B7 (achado nesta rodada, escrevendo o teste do item 3 "veredito nunca Approve" pedido pela revisão): o "pull-down" de result.Verdict para "comment" (B1-B5) nunca tinha efeito nenhum no --pr. reviewVerdictForLanguage (o texto "Verdict:" do corpo publicado) e formalReviewEvent (a ação formal real do GitHub, APPROVE/COMMENT/ REQUEST_CHANGES) nunca liam result.Verdict -- cada uma rederivava seu próprio veredito só de Issues/Suggestions/quality_degraded, sem nenhum conhecimento do gate. Um PR bloqueado ou inconclusivo pelo gate podia publicar "Verdict: Approve" no corpo E a ação real "APPROVE" no GitHub -- exatamente "aprovado com o defeito presente". Corrigido com duas linhas (uma em cada função, mesma prioridade que o checagem de quality_degraded já usa): if result.Verdict == "comment" { return copy.comment / "COMMENT" }. Essa correção saiu do escopo "só testes" que a rodada pediu porque o teste do item 3, escrito como pedido, provou que a premissa (o pull-down já funcionava) estava errada -- reportado aqui em vez de escondido atrás de um teste reescrito para passar.

    Declarado, não corrigido

    Uma falha de transporte/provedor genuína em --pr (llm.ErrAllProvidersFailed, llm.ErrBudgetExceeded) ainda retorna 1 ANTES do gate ser avaliado em runPRReview -- o gate nunca a vê, nenhum status é publicado, e gate.inconclusive não tem efeito sobre ela. Dado o prazo, esta entrega não estende essas duas saídas antecipadas para passar pelo gate; fazer isso corretamente exige decidir se --limite/um provedor totalmente fora do ar devem continuar sendo refusals antes de qualquer publicação (hoje) ou se tornam mais um motivo de gateInconclusiveReason com status/exit code próprios -- uma escolha de design que merece sua própria revisão, não uma correção apressada dentro de um prazo de 50 minutos. Fica nomeado no comentário de runPRReview (pr.go) exatamente onde esse desvio acontece.

    M13b (pedido pela revisão, item 2): não matado. TestAUR519PartialCoverageNeverCachedUnderBlock passa com e sem o guard !cachePartial em main.go ~981. Investigado: um arquivo coberto por ignore nunca chega a diff.Files/toSend (removido por config.FilterIgnoredPaths antes da partição do cache), então o cache nunca grava uma entrada PARA ELE; a entrada que É gravada (para o arquivo que FOI revisado por completo, ex. app.go) está correta e é segura de reusar independente da cobertura de outro arquivo.     Mecanismo (internal/review/skillrules.go)

    ParseSkillSections(skillFile, content, origin) []Rule lê cada ## e devolve uma Rule com id <base>#<slug>, título, descrição (limitada a 400 bytes), severidade (warning por padrão, ou a declarada na primeira linha do corpo como severity: error|warning|info) e Origin ("policy" ou "repo"). resolveRule resolve primeiro contra o catálogo embutido, depois contra esse conjunto dinâmico — o catálogo embutido nunca pode ser sombreado. enforceRuleCitations (internal/review/reviewer.go) aceita esse catálogo extra via Reviewer.SetDynamicRules; Reviewer.SetRuleCatalog repassa o catálogo fundido (embutido + dinâmico) ao PromptBuilder, para que o modelo seja ensinado exatamente os ids que o gate vai aceitar. Testes: TestAUR519ParseSkillSections (AC-007: uma seção nova vira citável sem mudança de código), TestAUR519EnforceRuleCitationsDynamic (AC-002: uma citação a uma seção que não existe é descartada e contada como não vinculada).

    Configuração (internal/config/gate.go, central.go)

    GateConfig.Threshold() normaliza fail_on reaproveitando o vocabulário de severidade de --fail-on (high|error, medium|warning, low|info), mais o alias critical que o próprio exemplo do card usa, mapeado no mesmo posto de high/error. InconclusiveMode() aceita block/warn (e bloquear/alertar). Config.Gate é validado em Parse. ApplyCentralPolicy estende a mesma precedência que já aplica a Rules/Ignore: sob política, só o Gate da política vale; um Gate do repositório é descartado com um aviso nomeado. Sem política, o Gate do repositório é seu próprio opt-in explícito (AC-005), inalterado. Testes: TestAUR519GateConfigThreshold, TestAUR519GateConfigInconclusive, TestAUR519ApplyCentralPolicyGate.

    Parse degradado à prova de forja (internal/prompt/parser.go)

    ParseModeKey/ParseModeDegraded/IsDegradedParse(result) expõem que um ParseReviewResponse veio do fallback de texto livre e não de uma resposta JSON válida. O decode de sucesso apaga qualquer valor que o próprio modelo tenha colocado em metadata.parse_mode antes de qualquer metadado do motor ser escrito — sem isso, uma resposta JSON válida e comum poderia forjar "metadata":{"parse_mode":"degraded"}. Teste: TestAUR519DegradedParseDetection. internal/review/reviewer.go foi unificado para usar esse único predicado em vez de manter sua própria cópia literal do aviso (ver nota de merge abaixo).

    Núcleo de decisão (cmd/aurumcode/policygate.go)

    evaluateGate(gate, acceptedOrigin, dynamic, issues, inconclusiveReason) decide, sem tocar stdout/stderr nem o cliente do GitHub: inconclusivo (quando inconclusiveReason != "") decide primeiro — bloqueia ou só alerta conforme gate.inconclusive, igual à prioridade que AUR-458 já dá a "não revisado" sobre "revisou e achou algo"; senão, qualquer achado na severidade do limiar ou acima, cuja regra dinâmica seja da origem aceita (policy sob política, repo no opt-in do repositório), reprova e nomeia a skill e a seção (AC-001). policyGateContext = "aurumcode/policy-gate" é o nome estável de status (AC-006), distinto do checkContext ("aurumcode/review") que AUR-439 já publica.

    Decisões de design tomadas por ambiguidade do card

    • fail_on é uma lista; o limiar é o menor rank entre as entradas. O card mostra fail_on: [critical, high] sem dizer como uma lista se traduz num limiar único. Tratá-la como "o menor rank listado" mantém a mesma leitura de --fail-on ("nesta severidade ou acima") aplicada a várias severidades em vez de uma.
    • critical é um alias de high/error. O exemplo do card usa critical, que --fail-on não aceita. Em vez de inventar uma quarta severidade só para o gate, critical foi mapeado no mesmo posto de high/error.
    • A declaração severity: de uma seção de skill usa só o vocabulário do motor (error/warning/info), não os aliases de CI do fail_on. Mantém uma seção de skill (Markdown livre, escrita por humano) numa gramática mínima e documentada, sem um segundo vocabulário de severidade divergente.
    • Dois nomes de status distintos: checkContext ("aurumcode/review", AUR-439, achado grave) e policyGateContext ("aurumcode/policy-gate", este card, compliance por skill) — para que um ruleset da organização possa exigir um sem o outro.
    • Rule.Origin foi adicionado ao tipo Rule já existente em vez de um tipo novo, para que resolveRule/enforceRuleCitations precisem de uma única forma de regra, sem conversão entre pacotes.
    • Na colisão de id entre política e repositório, a política vence. Um repositório não pode sombrear o id de uma regra da política com sua própria cópia de origem repo e, assim, tirá-la do conjunto aceito pelo gate (mergeDynamicRules).
    • O motivo de inconclusivo tem prioridade fixa: falha/skip do provedor primeiro, depois parse degradado, depois cobertura parcial — a mesma lógica de "não revisado supera achou algo" que AUR-458 já estabeleceu, agora estendida ao gate.
