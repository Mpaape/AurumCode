    AUR-424 — Extrator de documentação Go sem dependência externa

    Documento histórico do board. Pode descrever componentes removidos; para uso atual, consulte o guia do produto.

    Comando

    AURUMCODE_SOURCE_DIR=<diretório do projeto Go> \
AURUMCODE_OUTPUT_DIR=<diretório de saída> \
go run ./cmd/regenerate-docs

    Internamente, o comando acima delega a extração de páginas Go para internal/documentation/extractors/go.GoExtractor, através da chamada de registro já existente em cmd/regenerate-docs/main.go (registerLanguageExtractors):

    if err := register(goExtractor.NewGoExtractor(runner)); err != nil {
    return err
}

    Este card reescreve inteiramente internal/documentation/extractors/go; a assinatura NewGoExtractor(runner) é preservada de propósito para não exigir nenhuma mudança nesse call site.

    O que mudou

    Antes deste card, GoExtractor gerava documentação chamando o binário externo gomarkdoc via site.CommandRunner (runner.Run(ctx, "gomarkdoc", ...)). gomarkdoc não existe no sandbox offline (rede negada, sem instalação). Uma falha de exec.LookPath virava extractors.ToolUnavailableError, que o pipeline trata como "pular esta linguagem" — não como falha. Um projeto Go inteiro saía com zero páginas e exit 0, indistinguível de um projeto sem nada para documentar.

    A partir deste card, GoExtractor usa somente a standard library:

    • go/build.Context.MatchFile seleciona quais arquivos .go do diretório pertencem ao pacote documentado (arquivos *_test.go são ignorados);
    • go/parser.ParseFile lê cada arquivo selecionado;
    • go/doc.NewFromFiles associa comentários de pacote, tipo, função e método às suas declarações — exatamente como go doc/pkg.go.dev fazem;
    • go/printer.Fprint renderiza a assinatura de cada declaração (sem corpo de função, sem comentário duplicado).

    Alvo de build fixado (determinismo)

    O filtro de build constraints não é um detalhe: sem ele, um diretório com arquivos mutuamente exclusivos de plataforma (impl_linux.go e impl_windows.go, ou dois arquivos com linhas //go:build opostas) tem todos eles reunidos em um único pacote, e a página resultante anuncia uma superfície de API que nenhum build daquele pacote jamais contém. Isso reprova diretamente a cláusula do AC-001 "repetir a execução sobre a mesma entrada produz a mesma saída" no sentido que importa: a saída deixa de descrever uma configuração real.

    Por isso documentBuildContext() fixa o alvo em constantes, e não em runtime.GOOS/runtime.GOARCH:

    Campo Valor Razão
    GOOS linux Alvo fixo: a página não pode depender da máquina que a gerou.
    GOARCH amd64 idem.
    CgoEnabled false Caso contrário CGO_ENABLED do host decidiria o conteúdo.
    BuildTags vazio Caso contrário -tags do host decidiria o conteúdo.

    Consequência declarada: um arquivo *_windows.go, *_darwin.go ou guardado por //go:build windows não é documentado. Um diretório cujos únicos arquivos Go são excluídos pelo alvo fixado não é um pacote para efeito deste extrator, e não gera página nem erro.

    Nome de arquivo de saída injetivo

    O caminho do pacote (relativo à raiz do fonte) é achatado em um único nome de arquivo por outputBaseName. O esquema anterior trocava todo separador por _ e parava aí, o que não é injetivo: os diretórios a/b e a_b viravam ambos a_b.md, e o pacote escrito por último apagava a página do primeiro sem erro algum em ExtractResult.

    O esquema atual reserva _ como introdutor de escape, de modo que todo _ na saída é o primeiro byte de uma sequência de dois:

    Sequência Significado
    _u um _ literal dentro de um segmento de caminho
    __ um separador de caminho

    Como u ≠ _, a decodificação é determinística da esquerda para a direita, logo a codificação é injetiva. Nomes sem separador e sem _ — o caso comum, ledger — passam intactos. O pacote na raiz do fonte não tem segmento algum e recebe o nome root; o único caminho real que colidiria com ele (um diretório de topo chamado root) é deslocado para root__, um segmento final vazio que filepath.Rel nunca produz.

    Nenhum processo externo é iniciado; nenhuma chamada de rede é feita. GoExtractor.Validate agora sempre retorna nil: não há mais nada externo para verificar.

    O tipo do parâmetro runner deixou de ser site.CommandRunner e passou a ser uma interface local mínima (commandRunner, com o mesmo único método Run). A satisfação de interface em Go é estrutural, então o site.CommandRunner que main.go já passa continua sendo aceito sem nenhuma mudança nesse arquivo; o pacote internal/documentation/extractors/go deixou de importar internal/documentation/site por completo, porque não tem mais nada para mandar um runner executar.

    Opções (via variáveis de ambiente lidas por cmd/regenerate-docs)

    Variável Efeito
    AURUMCODE_SOURCE_DIR Raiz do projeto a documentar.
    AURUMCODE_OUTPUT_DIR Diretório onde as páginas Markdown são escritas.
    AURUMCODE_INCREMENTAL Quando true, pula pacotes cujo .md já é mais novo que o fonte.

    GoExtractor.WithIncrementalMode expõe o mesmo controle programaticamente.

    Exit codes

    Estes são os exit codes do próprio GoExtractor.Extract (biblioteca) e do aceite deste card (tests/acceptance/AUR-424.sh), não os do binário completo cmd/regenerate-docs (que soma o resultado de todas as linguagens):

    • Extract retorna error != nil apenas para uma entrada inválida (idioma errado, diretório de origem inexistente, diretório de saída não gravável) ou cancelamento de contexto; um pacote individual que falhar ao parsear é reportado em ExtractResult.Errors e não interrompe os demais.
    • tests/acceptance/AUR-424.sh: ver "Exit codes do aceite" mais abaixo.

    $ AURUMCODE_SOURCE_DIR=./tests/fixtures/docs/goproject AURUMCODE_OUTPUT_DIR=./site \
    go run ./cmd/regenerate-docs
