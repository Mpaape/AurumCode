    AUR-542: scripts e2e de cards done que ainda falham voltam a provar o prometido

    O que foi medido

    AUR-541 (2026-10-02) auditou tests/e2e/*.sh que alimentam AURUMCODE_LLM_FIXTURE e corrigiu o gate de evidencia nas fixtures, mas encontrou seis scripts que falham por motivos ALEM desse gate: AUR-438, AUR-443, AUR-448, AUR-449, AUR-451, AUR-459. Este card roda cada um via .board/bin/go-shared exec contra este worktree, mede a causa raiz, e decide: regressao de produto (corrigir dentro dos paths deste card) ou teste desatualizado (corrigir o teste, sem afrouxar nenhum gate nem mudar o que o card de origem prometeu).

    Metodo: cada script foi executado isolado antes de qualquer edicao, o primeiro fail()/infra() encontrado foi tratado como a causa, e o binario foi reconstruido e reexecutado apos cada correcao candidata para confirmar o novo resultado -- nunca inferido.

    AUR-443: docs nao existe mais, e a mensagem de "sem provedor" mudou sob AUR-443

    Causa

    Duas causas distintas, nao relacionadas entre si:

    1. aurumcode --help, docs --help e o bloco final do script testavam o subcomando docs (gerado por cmd/regenerate-docs). Esse comando foi removido do produto pelo commit 670c7f6 ("Focus AurumCode on code review and publish interactive documentation", 2026-09-12), um pivo de produto deliberado e anterior a este card -- git ls-files cmd/regenerate-docs e vazio em main, e o binario hoje responde aurumcode: unknown command "docs" (exit 2) para qualquer invocacao. AUR-490 (done) ja trata essa remocao como fato assentado.
    2. O script chama review --base HEAD~1 sem provedor e espera exit 1 com stdout vazio. AUR-490 (done, integrado em main antes deste card) mudou esse caminho deliberadamente (seu proprio registro de entrega: "review --base sem provedor configurado deixa de sair 1 incondicionalmente"): hoje sai 0 por padrao (roda so analise deterministica) a menos que o chamador peça --exigir-qualidade (AUR-458), e o stdout passa a sempre trazer o resumo e o diagrama mermaid (AC-002 do AUR-490) em vez de ficar vazio ou conter so a linha de achado.

    Decisao

    Teste desatualizado nos dois pontos. docs ja nao existe no produto por decisao de outro card, anterior e integrado; manter a asserção testaria uma capacidade que o produto deliberadamente abandonou. O exit-code e o formato de stdout de "sem provedor" tambem sao decisao deliberada e integrada do AUR-490, nao uma regressao deste card para corrigir.

    Antes

    tests/e2e/AUR-443.sh falhava em help_missing_docs (grep por docs no --help de topo).

    Depois

    Removidas as asserções sobre docs (linhas que verificavam --help listar docs, docs --help, docs --this-flag-does-not-exist, e o bloco final que rodava docs --source ... --output ...); a secao 7 ("review --base's published contract") passou a comparar so a ULTIMA linha do stdout (tail -n1) contra No issues found. em vez do stdout inteiro, porque o AUR-490 sempre antepõe o bloco de resumo/diagrama; a secao 4 ("no provider configured") passou a esperar exit 0 (o novo padrao) em vez de 1. tests/e2e/AUR-443.sh sai 0.

    AUR-448: "sem provedor" nao tinha mais a mensagem completa da fixture

    Causa

    O cenario 1 (no_provider_wrong_exit) tambem colide com a mudanca do AUR-490: review --base HEAD~1 sem provedor agora sai 0, nao 1. Mas, ao investigar mais a fundo, a mudanca do AUR-490 tambem substituiu, no caminho padrao (sem --modelo explicito), a mensagem completa que errNoProviderConfigured carrega -- com rule_id, severity, um exemplo real do catalogo e o ponteiro para known-problem-response.json -- por uma linha curta ("no LLM provider configured: quality review skipped; running deterministic analysis only"). Essa e exatamente a mensagem que AUR-448 e AUR-443 foram escritos para proteger (a promessa do AUR-448: "a mensagem que ensina o formato do fixture mostra a forma COMPLETA que o motor exige"). Medido diretamente em cmd/aurumcode/main.go: antes deste card, nenhum caminho alcancavel sem --modelo explicito imprimia mais "rule_id", "severity", security/hardcoded-secret ou tests/fixtures/review/known-problem-response.json no stderr.

    Decisao

    Regressao de produto real, dentro do escopo deste card (cmd/aurumcode esta em paths). O AUR-490 tinha o direito de mudar o exit code (decisao dele, registrada e revisada) mas apagou, como efeito colateral nao documentado, uma mensagem que outro card done prometia explicitamente. Conserto aditivo: a branch qualitySkipped de cmd/aurumcode/main.go (em torno da linha 868) agora imprime a mensagem curta do AUR-490 E, numa segunda linha, o texto completo de errNoProviderConfigured (%v) -- sem mudar a linha curta, o exit code ou o stdout. Nao e uma reversao do AUR-490: o exit code continua 0 por padrao.

    Antes

    AUR-438: achado geral (fora das linhas adicionadas) continua inalcancavel -- NAO CORRIGIDO

    Causa

    Confirmado exatamente como o AUR-541 mediu: internal/review/scope.go::filterModelIssues descarta QUALQUER achado fora das linhas adicionadas do diff (contador OutsideAddedLines) ANTES de checar evidencia/impacto/verificacao -- mesmo quando o achado carrega as tres provas completas (como a fixture do proprio AUR-438.sh planta em docs/notas.md:99). cmd/aurumcode/pr.go ja tem a logica downstream inteira para classificar um achado sobrevivente como inline (isInlineEligible, que chama review.IsChangedLine -- a MESMA funcao containsSide que filterModelIssues ja usou para decidir se o achado sobrevive) ou geral (o else que chama PostIssueComment por achado). Como as duas checagens sao identicas, todo achado que sobrevive a filterModelIssues TAMBEM passa isInlineEligible -- o que decide entre os dois ramos de publicacao e so a flag --na-linha (inlineComments): sem ela, TODO achado sobrevivente (mesmo um dentro das linhas adicionadas) sai pelo ramo geral; com ela, o ramo geral fica inalcancavel para qualquer achado de modelo, porque nenhum achado fora do diff chega viva o bastante para testar a flag. O recurso de comentario geral de PR prometido pelo AUR-438 ("problema fora das linhas alteradas vira comentario geral em vez de sumir") esta, na pratica, inalcancavel para o caso que ele foi desenhado para cobrir.

    Decisao medida e por que fica fora deste card

    Uma correcao exigiria mudar internal/review/scope.go para distinguir "arquivo nunca tocado pelo diff" (deve continuar descartado -- e o proprio motivo de existir do gate: impedir que o modelo fale com autoridade sobre codigo nao tocado) de "arquivo tocado, linha fora do hunk" (candidato a comentario geral, ainda sujeito ao gate de evidencia). Essa distincao foi prototipada e imediatamente CONTRADIZ dois testes unitarios existentes e deliberados em internal/review/scope_test.go (TestFilterModelIssuesRejectsUnscopedAndUnprovedFindings e TestDeletionRegressionUsesOldSideWithoutAdmittingUntouchedCode), que fixam o comportamento atual -- inclusive para um achado DENTRO do mesmo arquivo tocado mas em coordenada (side/linha) errada -- como correto e intencional. Resolver esse conflito exige decidir qual dos dois comportamentos documentados (o do AUR-438: achado geral some; o dos testes de scope_test.go: qualquer posicao fora da linha exata e rejeitada, mesmo dentro do mesmo arquivo) e o certo, e essa decisao afeta internal/review/scope.go, que todo achado do motor passa por -- risco e escopo maiores do que este card, que e sobre e2e scripts, deveria assumir sem uma revisao dedicada. Non-goals deste card proibe "afrouxar o gate de escopo e evidencia"; mudar scope.go sem decidir essa tensao seria exatamente esse risco. Recomendacao: abrir um card dedicado para decidir e, quando decidido, atualizar internal/review/scope.go e internal/review/scope_test.go juntos. Aberto: AUR-545.

    Antes e Depois

    Sem mudanca. tests/e2e/AUR-438.sh continua saindo 1 com AUR-438/AC-001/missing_general_finding -- exatamente a causa medida acima, nao mascarada.
