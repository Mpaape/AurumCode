    Tutorial: plugin externo na validação agendada (scheduled.plugins)

    Objetivo

    Um scanner externo (por exemplo, um harness agêntico de vulnerabilidade) roda na validação agendada, no próprio container, e os achados dele vão para a aba Security (code scanning), que exige permissão de escrita, ou, num repositório privado sem Code Security, para issues do próprio repositório. Nada do achado aparece no log do Actions, no resumo do job, em artefato ou na PR, que num repositório público são públicos. Ao final você terá visto, com o binário real do produto:

    1. o ingest de um plugin: SARIF só com os verdadeiros positivos e a saída do comando só com contagens;
    2. falso positivo, canal posture e achado sem veredito fora do envio, contados;
    3. dúvida nunca some: candidato que o plugin não conseguiu verificar vira alerta de aviso "não verificado";
    4. o job plugins do workflow reutilizável (conferência estática);
    5. repositório privado sem Code Security: os achados viram issues do próprio repositório, uma por achado, abertas, mantidas, fechadas e reabertas a cada varredura (contra um GitHub falso local);
    6. quando falha: plugin degradado e cobertura perdida com zero achados — inconclusivo, exit 1 e nenhum SARIF (um SARIF vazio fecharia os alertas abertos); e repositório público, onde achado nunca vira issue.

    O contrato completo está em plugins agendados. Cada saída abaixo vem de uma execução real, registrada em demo/tutoriais/plugin-agendado/out/ e conferida por run.sh --check. Os blocos marcados com o caminho são os arquivos da demonstração, byte a byte.

    Como a demonstração prova isso sem modelo e sem rede

    O plugin de exemplo (plugin-exemplo/plugin.sh) faz o papel do harness: não chama modelo nenhum, só copia para security-scan/ da árvore um findings.json e o SARIF do harness sintéticos do cenário pedido. O aurumcode plugin list e o aurumcode plugin ingest rodam na imagem do produto, sem rede. O aurumcode plugin issues também roda na imagem do produto, mas fala só com um GitHub falso em 127.0.0.1 (github-falso-issues.py, que guarda as issues em memória e anota cada requisição), nunca com o GitHub.

    #!/usr/bin/env bash
# Plugin de exemplo OFFLINE: faz o papel do harness sem modelo e sem rede.
# Copia para <arvore>/security-scan/ o findings.json e o SARIF do harness do
# cenario pedido e sai com exit 0, como o harness quando conclui (inclusive
# quando perdeu cobertura: o ingest le degraded e o SARIF do harness).
#
#   plugin.sh <cenario> <arvore>
#   cenarios: tres-achados | misto | nao-verificado | degradado | cobertura-perdida
set -euo pipefail
cenario="$1"; arvore="$2"
aqui="$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd -P)"
saida="$arvore/security-scan"
rm -rf "$saida"; mkdir -p "$saida"
cp "$aqui/fixtures/$cenario/findings.json" "$saida/findings.json"
cp "$aqui/fixtures/$cenario/report.sarif" "$saida/alvo_20261014T000000_report.sarif"
exit 0

    Pré-requisitos

    • git, docker, bash e python3 no host. Nada mais.
    • A imagem do produto, construída do Dockerfile da raiz (o run.sh faz isso sozinho).

    Rodar a demonstração

    bash demo/tutoriais/plugin-agendado/run.sh all
bash demo/tutoriais/plugin-agendado/run.sh --check

    A configuração do repositório de exemplo declara um plugin:

    scheduled:
  plugins:
    - name: vvah
      dockerfile: plugins/vvah/Dockerfile
      env: [ANTHROPIC_API_KEY, VVAH_MODEL]
      output:
        format: vvah-findings
        path: security-scan/findings.json
      timeout_minutes: 90

    Caso 1: ingest

    O plugin acha três casos: dois verdadeiros positivos e um falso positivo. O ingest grava o SARIF com os dois primeiros (regra plugin/vvah/<cwe>, fingerprint case_id do harness, categoria aurumcode/plugin/vvah) e o texto do achado passa pelo filtro de segredos. O que o comando imprime é só a contagem.

    bash demo/tutoriais/plugin-agendado/run.sh ingest

    == ingest
$ aurumcode plugin list --json --repo /work
[{"name":"vvah","dockerfile":"plugins/vvah/Dockerfile","args":[],"env":["ANTHROPIC_API_KEY","VVAH_MODEL"],"timeout_minutes":90,"job_timeout_minutes":120,"output":{"format":"vvah-findings","path":"security-scan/findings.json"}}]
exit_code=0

    Caso 2: fora do envio

    Só achado do canal principal com veredito TRUE_POSITIVE vira alerta. O falso positivo, o canal posture e o achado sem veredito só contam.

    bash demo/tutoriais/plugin-agendado/run.sh fora-do-envio

    Caso 4: o job agendado

    O job plugins do .github/workflows/review.yml roda em schedule e em workflow_dispatch na branch padrão. Num pull_request os jobs são pulados pelo if: (nenhum passo roda); o primeiro passo, que sai com exit 1 em qualquer outro evento, é defesa em profundidade. A saída do plugin vai para um arquivo em $RUNNER_TEMP que nunca é impresso nem vira artefato. O passo "Choose destination" decide o destino pela visibilidade: no destino security o SARIF segue direto para o code scanning; no destino issues o passo "Sync issues" roda aurumcode plugin issues (sem upload-sarif), só depois de um ingest conclusivo.

    bash demo/tutoriais/plugin-agendado/run.sh workflow

    == workflow
gatilho: schedule, ou workflow_dispatch na branch padrao
pull_request: os jobs sao pulados pelo if (nenhum passo roda)
defesa em profundidade: se rodasse em outro evento, o primeiro passo sairia com exit 1
timeout do job: o do plugin mais a folga fixa; rc 124 vira uma linha no log
sem upload-artifact e sem resumo do job
saida do plugin: arquivo em RUNNER_TEMP, nunca impresso
envio: upload-sarif fixado por SHA
categoria: aurumcode/plugin/<nome>
log: so a contagem de alertas
upload-sarif: so no destino security
destino issues: plugin issues depois do ingest conclusivo, sem upload-sarif
chamador: issues: write documentado
RESULTADO: o job plugins publica na aba Security, ou em issues do proprio repositorio privado sem Code Security
NAO EXECUTADO AQUI: o envio ao code scanning e as issues reais (nao ha runner nem GitHub neste ambiente)

    Caso 5: issues no repositório privado sem Code Security

    Num repositório privado sem GitHub Code Security não há aba Security para alertas de código: os achados viram issues do próprio repositório, que só os colaboradores veem. Cada issue leva na primeira linha do corpo um marcador oculto com o fingerprint estável do achado (<!-- aurumcode-plugin:<nome>:<fingerprint> -->) e o rótulo aurumcode-plugin:<nome>. O título só tem campos estruturados (regra, arquivo, linha, severidade); a descrição redigida fica no corpo, num bloco de código. Três varreduras seguidas contra o GitHub falso:

    1. dois verdadeiros positivos: abre 2 issues;
    2. só um deles continua: mantém a que continua sem duplicar e fecha a que sumiu, com um comentário;
    3. o achado fechado volta, com outros novos: reabre a issue dele e abre as novas;
    4. uma pessoa fecha uma issue cujo achado continua: a decisão humana vale, a issue fica fechada, sem escrita nela, e conta como "dispensada por pessoa". Quem fechou é decidido pelo autor do último evento closed da issue, nunca pelo último comentário: só a issue que o próprio plugin fechou é reaberta.

    Falha 3: repositório público e varredura inconclusiva

    Em repositório público achado nunca vira issue: o comando confere a visibilidade pela API e recusa (exit 1) antes de qualquer escrita; uma visibilidade que não pode ser lida é tratada como pública. E uma varredura inconclusiva (o ingest não gravou SARIF) não faz nenhuma chamada ao GitHub: as issues abertas ficam como estão.
