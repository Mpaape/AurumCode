## Outcome

Um visitante novo encontra um site bonito, legivel e responsivo que apresenta
code review, documentacao e publicacao, com uma jornada copiavel para comecar.
O README e o guia concordam com o produto atual. O build publica os assets
necessarios e mantem guias e API acessiveis sem expor prompts ou skills internos.

## Non-goals

- Nao mudar o motor de review, o gerador, a API ou o contrato da CLI.
- Nao instalar servicos de analytics, fontes remotas ou bibliotecas de UI.
- Nao publicar no GitHub nem alterar tags durante o build do candidato.
- Nao editar as specs historicas ou fingir que um comando foi executado.

## Acceptance scenarios

- AC-001: a landing tem hierarquia visual deliberada, tipografia legivel,
  identidade em tons de ouro e neutros, exemplos curtos por feature e CTA
  principal para o inicio rapido; API e guias permanecem encontraveis.
- AC-002: a rotina real de staging usada pelo workflow copia index, config,
  Gemfile, guias publicos e assets locais; omite prompts, skills, docs/specs e
  nao modifica a origem. A acceptance executa essa rotina em temporario e
  verifica os arquivos resultantes; retirar a copia dos assets deve falhar.
- AC-003: build Jekyll em container e observacao no navegador em desktop e
  viewport 390px comprovam ausencia de overflow global, links principais
  validos, foco visivel, contraste legivel e nenhuma referencia a asset ausente.
- AC-004: README e guia oferecem primeiro o workflow reutilizavel para review,
  explicam os dois secrets e modelo configuravel, e um caminho local curto.
  Suporte Rust/C# nativo, diferencas entre comandos e limites sao corretos.
  Nenhum link incondicional aponta para relatorio editorial opcional ausente.

## Public contract

URLs dos guias e API preservadas. Sem dependencia remota nova para visitantes.
Customizacao usa o tema Jekyll existente e assets locais responsivos.

## Acceptance

container_profile: `bootstrap-readonly-v1`

accept: `./.board/bin/oci-run --profile bootstrap-readonly-v1 --card AUR-487`

O aceite OCI exercita o staging real e a mutacao de AC-002. A validacao adicional
obrigatoria AC-003 usa Ruby/Jekyll em container limitado e navegador; registrar
comandos, resultados e screenshots do SHA candidato. Nao declarar beleza ou
links funcionais apenas a partir de grep de fontes.

## Skeptical mutations

- MUT-001: remover a copia de assets da rotina real de staging; o mesmo teste
  nominal deve falhar por asset ausente. Restaurar reproduz exit 0.
- MUT-002: remover destino do CTA principal no site renderizado; a verificacao
  de navegacao deve detectar o link quebrado.

## Validation

- Integration: `tests/acceptance/AUR-487.sh::AC-001` executa staging real.
- E2E: build Jekyll e navegador sobre o payload do mesmo candidato.
- Unit: not-applicable: conteudo e estilos sem novo algoritmo de dominio.
- Contract: staging preserva URLs e separa conteudo publico de contexto interno.

## Compatibility, migration, rollback

Sem migracao de dados. Reverter o commit restaura apresentacao anterior.
O reviewer confere o diff completo, o staging nominal/mutante e a navegacao
renderizada no mesmo SHA; nao altera o candidato.
