## Outcome

Pedido do dono (2026-10-14): incluir um agente de scan de vulnerabilidade
(o harness agentico publico https://github.com/visa/visa-vulnerability-agentic-harness,
Apache-2.0, Python) "como plugin externo da validacao agendada", e a
vulnerabilidade NAO pode ficar publica no repositorio: so numa area
gerenciada. Em repositorio publico, log do Actions, resumo do job,
anotacoes, artefatos de run, comentario e anotacao de PR sao publicos; a
lista de alertas de code scanning (aba Security) exige permissao de escrita.

Depois deste card:

1. Ponto de extensao novo, generico: `scheduled.plugins` na configuracao
   (repo ou politica central; sob politica `required: true` o repo nao
   remove nem afrouxa). Cada entrada: `name`, `image` fixada por digest
   (`@sha256:`) OU `dockerfile` lido da ref confiavel, `args`, `env` (so
   NOMES de variaveis; valores vem de secrets do chamador), `output`
   (`format: sarif | vvah-findings`, `path` relativo a arvore varrida),
   `timeout_minutes`. O binario nao embute plugin nenhum: o plugin roda em
   container proprio, sem o docker.sock, com a arvore montada somente
   leitura numa copia descartavel.
2. `aurumcode plugin list --json` (le a configuracao confiavel) e
   `aurumcode plugin ingest --name N --format F --input P --repo DIR --sarif OUT`:
   a saida do plugin e dado nao confiavel. Caminho absoluto, `..`, fora da
   arvore ou inexistente e recusado (achado nao some: o ingest reprova);
   texto passa pelo filtro de segredos; SARIF 2.1.0 com
   `tool.driver.name` `AurumCode plugin <nome>`, `ruleId` estavel
   (`plugin/<nome>/<cwe ou classe>`), `partialFingerprints` (no harness:
   `case_id`), `automationDetails.id` `aurumcode/plugin/<nome>/`,
   `security-severity`. Formato `vvah-findings`: `findings.json`
   (`schema_version` 1.x; outro major recusa); so achados do canal
   principal com veredito `TRUE_POSITIVE` (os outros contam no resumo);
   `degraded: true`, SARIF `executionSuccessful: false`, cobertura oca,
   arquivo ausente, JSON invalido ou plugin com exit != 0 = inconclusivo:
   exit 1 e NENHUM SARIF escrito (um SARIF vazio fecharia os alertas
   abertos). Stdout do ingest: so contagens.
3. Job `plugins` no workflow reutilizavel: roda em `schedule` e
   `workflow_dispatch`, so na branch padrao, nunca em `pull_request*`
   (o `if:` pula os jobs; um passo de recusa com exit != 0 fica como defesa
   em profundidade); le a configuracao da ref padrao; para
   cada plugin: monta a imagem, roda com stdout/stderr para arquivo em
   `$RUNNER_TEMP` que nunca e impresso nem vira artefato, ingere e envia o
   SARIF direto para code scanning (`upload-sarif` fixado por SHA, categoria
   `aurumcode/plugin/<nome>`, permissao `security-events: write` concedida
   pelo chamador). Nada de `upload-artifact`, de resumo com achado ou de
   `::error` com texto do achado: o log diz so "N alertas enviados para a
   aba Security (visivel so para quem tem escrita)". Repo privado sem
   GitHub Code Security: o envio falha e o job falha dizendo isso; nunca
   cai para um canal publico. Entrada da politica exige `image@sha256:`
   (um `dockerfile` seria lido do repositorio alvo, que poderia trocar o
   plugin). Candidato que o verificador do plugin nao decidiu vira alerta
   "nao verificado"; duvida nunca some.
4. Exemplo pronto do harness: `demo/plugins/vvah/` com Dockerfile que
   instala o harness fixado por commit (4128e870377850db16cb082115105cc8ee6f1a72)
   e um perfil so de descoberta: exploracao viva `enabled: false` (com
   `EV_API_COLLECTION` presente o harness recusa, exit 2), S10/S11
   desligados, `ingest_*` removidos (sem envio a hub), `auto_exclude: false`,
   `scan_progress.enabled: false`, `--stop-after s9`, `--config` fora da
   arvore, `VVAHARNESS_NO_LOCAL_CONFIG=1`, variaveis de rastreamento
   (LANGSMITH/LANGCHAIN) ausentes; provedor por `OPENAI_API_KEY`/`OPENAI_BASE_URL`
   e modelo por papel.
5. Doc `docs/plugins-agendados.md` (contrato, o que fica publico e o que
   nao fica, licenca, custo, repo privado) e tutorial executavel
   `plugin-agendado` com o plugin de exemplo offline (fixture, sem modelo).

## Non-goals

Embutir ou clonar o harness no binario; rodar plugin na PR; exploracao viva
ou remediacao automatica; o gate da PR consultar alertas sigilosos (fica
para card proprio, opt-in); destino alternativo para repo privado sem Code
Security (card proprio); mudar o job agendado de dependencias.

## Acceptance scenarios

- AC-001: config: plugin sem digest e sem dockerfile, `env` com valor, `output.path` absoluto ou com `..` e nome repetido sao recusados na leitura; sob politica `required: true` o repo nao remove a entrada.
- AC-002: ingest `vvah-findings` de fixture com 3 achados (2 TRUE_POSITIVE, 1 FALSE_POSITIVE) gera SARIF valido com 2 resultados, ruleId/fingerprint/categoria estaveis e segredo redigido; stdout so com contagens, sem titulo, arquivo ou descricao de achado.
- AC-003: ingest com `degraded: true`, JSON invalido, schema_version 2.x, plugin exit != 0 ou arquivo ausente: exit 1 e nenhum SARIF escrito.
- AC-004: achado com caminho absoluto, `..` ou fora da arvore: ingest reprova (nunca descarta em silencio).
- AC-005: workflow: o job `plugins` so roda em schedule/workflow_dispatch na branch padrao, e pulado em pull_request (com passo de recusa como defesa), nao usa upload-artifact nem job summary com achado, redireciona a saida do plugin, envia com upload-sarif fixado por SHA e categoria aurumcode/plugin/<nome>; actionlint/yaml valido.
- AC-006: tutorial plugin-agendado: 3 casos de uso + 1 de falha, `run.sh all` e `--check` verdes, blocos da doc iguais aos arquivos da demo.
- MUT-001: o ingest escrever SARIF com `degraded: true` faz AC-003 falhar.
- MUT-002: imprimir o titulo do achado no stdout do ingest faz AC-002 falhar.
