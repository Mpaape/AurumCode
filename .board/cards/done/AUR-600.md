## Outcome

Medido na PR #104 (lote dev -> main, 2026-10-07): com `gate.fail_on: [error]`
e dois achados `warning`, o status `aurumcode/policy-gate` passou, mas o
parecer publicou **Veredito: Alterações solicitadas** e "A revisão encontrou
2 achado(s) bloqueante(s) que devem ser tratados antes do merge". O leitor
recebe duas respostas opostas; o parecer afirma bloqueio que o gate nao
aplicou. Tambem pendente do AUR-599: quando todos os itens do status do CI
sao descartados, a secao some em vez de dizer em uma linha que nada falhou
nesta execucao (precisa de chave em internal/i18n).

Com este card: com gate declarado, "bloqueante" no parecer significa
exatamente o que o gate reprova; achados abaixo do limiar sao contados como
nao bloqueantes; o veredito do parecer segue o gate (reprova -> alteracoes
solicitadas; passa com achados abaixo do limiar -> comentario/aprovado com
ressalvas, nunca "alteracoes solicitadas"); sem gate o comportamento atual e
mantido. A secao de status do CI mostra a linha "nada falhou nesta execucao"
quando todos os itens foram descartados.

## Non-goals

Mudar o gate ou o limiar; esconder aviso; mudar o formato da review formal
alem do texto.

## Acceptance scenarios

- AC-001: fail_on error + so warnings: gate passa, parecer nao diz "bloqueante" nem "Alterações solicitadas", lista os avisos como nao bloqueantes.
- AC-002: fail_on error + um error: parecer diz 1 bloqueante e alteracoes solicitadas, coerente com o gate.
- AC-003: sem gate declarado, texto atual preservado.
- AC-004: status do CI com todos os itens descartados mostra a linha unica.

## Skeptical mutations

- MUT-001: Contar warning como bloqueante com fail_on error reprova AC-001.
- MUT-002: Veredito ignorar o gate reprova AC-001/AC-002.
