## Outcome

Uma TestProposalV1 de JavaScript só recebe verified após aplicação em worktree descartável, runner JavaScript pinado, repetição anti-flake, delta de cobertura normalizado e prova de que reverter a mudança funcional torna o teste vermelho pelo motivo esperado.

## Non-goals

- Verificar testes de browser, DOM ou end-to-end e resolver dependência npm ausente; `internal/application/testverify/javascript` valida apenas unit tests que rodam com o cache já pinado.
- Instalar package, consultar registry, usar cache mutável ou executar fora do profile polyglot-toolchain-v1.

## Preconditions

- A proposta de AUR-253, o aplicador seguro e os gates de teste estão ligados à mesma CandidateIdentityV1.
- Toolchain, package cache, comandos e fixtures estão pinados; o worktree é descartável e sem segredo.

## Postconditions

- O TestVerificationV1 registra digests de proposta, worktree e toolchain Node, o comando do runner JavaScript pinado, os resultados green das repetições anti-flake, o delta de cobertura normalizado e a prova revert-red.
- Erro de resolução de módulo, runner ou engine indisponível, timeout, suíte vazia, test.skip, divergência entre repetições ou teste que permanece verde após o revert produz incomplete ou fail com código próprio, nunca verified.

## Acceptance scenarios

### AC-001: Verificar proposta de unit test JavaScript

- Given: três TestProposalV1 de JavaScript em `tests/fixtures/testgen/javascript/verification`: uma nominal, uma vacuous sem assertion efetiva e uma que permanece verde com a mudança funcional revertida.
- When: o verifier aplica cada proposta em clone descartável e executa runner JavaScript pinado no profile pinado.
- Then: o registro marca `verified` só para a nominal, com o runner JavaScript pinado em exit 0 a cada repetição e revert-red no teste esperado; as demais saem 1, a insensível com `AUR-414/AC-001/revert-insensitive`.

## Security and privacy

- Proposta, source e output do toolchain são dados não confiáveis; comandos vêm da allowlist do profile, não da resposta do modelo.
- Worktree é descartável, mounts do host são zero, rootfs é read-only e escrita existe apenas em tmpfs bounded.
- Credentials, env, prompts/respostas brutos e canários não entram em stdout, logs, cache ou evidência.

## Documentation

- `docs/specs/AUR-414.md` fixa toolchain, comandos, matriz green/repeat/coverage/revert, estados inconclusivos e diagnóstico.

## Compatibility, migration, rollback

- TestProposalV1 permanece inalterada; versões incompatíveis de TestVerification criam novo schema.
- Nenhum teste é publicado automaticamente; consumidor decide aplicar artefato verificado por outro card.
- Rollback remove apenas verifier e fixtures javascript, preservando propostas e source.

## Review

- Reviewer: one independent reviewer reads the exact immutable candidate in a clean detached worktree and checks every changed hunk, the public contract, paths/read_paths, acceptance, declared selectors, mutations, profile/runtime compatibility, security boundaries, and exit-code handling.
- Independence: the reviewer is separate from the builder and does not edit the candidate or write evidence in the coordinator checkout. No extra review role is required.
- Verdict: approve only on raw exit 0 with real assertions. Runtime, loader, image, dependency, or other infrastructure failures are blocked or inconclusive, never approval. The validator reruns the declared acceptance on the same SHA when validation is not none.

## Evidence

Only the coordinator writes sanitized evidence under .board/evidence/<card-id>/; tests and builders emit observations only. Evidence binds the exact candidate SHA, review verdict, acceptance/validation exits, mutation result when declared, clean tree, and artifact hashes. Never store secrets, raw prompts/responses, credentials, environment values, or chain-of-thought.
